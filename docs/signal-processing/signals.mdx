# Signals & Noise

<Difficulty level="Easy" />

<Abstract>
Every sensor reports the true value plus noise, slow drift, and the occasional wild spike, and the
shape of that corruption decides which filter you should reach for. This lesson characterises exactly
how sensor data lies before we build anything to clean it up.
</Abstract>

A filter is only worth building if the raw data is untrustworthy. It is. This page characterises
exactly *how* sensor data is corrupted, because the structure of the noise determines which filter
you reach for next.

<Problem>

## Every sensor reports the truth plus garbage

A **signal** is a value that changes over time — an arm angle, a distance to the wall, a wheel
velocity. You never observe it directly; you observe a **sensor reading**, which is the true value
plus error. Feed that raw reading into a controller and the error propagates: a PID derivative term
amplifies jitter into motor chatter, a distance sensor's momentary spike trips an autonomous state
transition, a slow bias steers odometry off the field.

<Formula>
  <Amber>measurement</Amber> = <Teal>true value</Teal> + <Rose>noise</Rose>
</Formula>

Four distinct corruptions, each demanding a different defence:

- **Jitter**: fast, small, random wobble around the truth. The common case.
- **Spikes (outliers)**: occasional wild readings: a loose connector, a reflection, a glitch.
- **Bias**: a fixed offset, present in full from the first sample and constant thereafter. Averaging
  never sees it; only calibration removes it.
- **Drift**: an error that *grows* over time as small relative errors accumulate. No amount of averaging
  removes it either — you need a second, absolute reference, and that reference had better not be biased.

:::tip[Which sensors actually need this?]
Quadrature-encoder position is often cleaner than an analog reading, but it is quantized and can still
miss edges or count false edges because of wiring, electrical noise, or excessive rate. Filtering a
healthy encoder position often adds unnecessary lag; encoder *velocity* is different because
differencing positions amplifies tick quantization and timing jitter. The signals
genuinely worth filtering are the ones with real, roughly bell-shaped noise: **analog sensors** —
distance sensors, analog absolute encoders, current sensors — and **vision**, where a tag's reported
pose jitters from frame to frame. Those are the running examples in this module.
:::

<NoiseAnatomyExplorer />

This Desmos-style graph gives each corruption its own slider, so you can study its *shape* in
isolation. **Jitter** scatters the amber readings symmetrically around the center — it carries no
information, and averaging cancels it. **Drift** scatters nothing: it moves the *center itself* (the
dashed line walks away from the truth), so no amount of averaging will ever remove it — you need a
second, absolute reference. A **spike** is neither: one absurd reading that any average will happily
swallow and be wrong about for a while. Three shapes, three different defences — which is why the
lessons ahead are a toolbox, not one magic filter: smoothing attacks jitter, sensor fusion attacks
drift, and outlier rejection handles spikes.

</Problem>

<Theory>

## Sampling, and what noise looks like

A Control Hub does not read sensors continuously; it **samples** them tens to hundreds of times per
second (see [From Math to a Loop](../software-architecture/discretization.mdx) for why the rate
matters). Every filter in this track operates on that stream of samples and answers one question:
*given the readings so far, what is the best estimate of the true value?*

The demo synthesises a known true signal (green) and a sensor that reports it with the three
corruptions above (amber dots). Increase the noise until the truth disappears into the scatter —
then consider controlling a mechanism from those dots alone.

## Measure your sensor before you filter it

Good filtering starts with knowing how noisy a sensor actually is. Sample it while the mechanism is
held still and compute the standard deviation — that number sizes every filter that follows.

<JavaCode league="FTC" label="Characterise a sensor's noise without blocking the loop">{`private static final int N = 200;     // samples to collect
private int count;
private double mean;
private double m2;

// Hold the mechanism perfectly still and call this once per loop. Anything
// the sensor reports now is noise, because the truth is not moving.
void update(double x) {
    if (count >= N) return;           // done; never block waiting for more
    count++;

    double delta = x - mean;
    mean += delta / count;
    double delta2 = x - mean;         // recomputed AFTER the mean update
    m2 += delta * delta2;

    if (count == N) {
        double std = Math.sqrt(m2 / count);
        report(mean, std);
    }
}`}</JavaCode>

<Exercise title="Why not sum and sum-of-squares?">

That is Welford's algorithm. The obvious alternative — accumulate $\sum x$ and $\sum x^2$, then use
$\operatorname{Var} = E[x^2] - E[x]^2$ — can suffer catastrophic cancellation when the mean is much
larger than the spread, especially in lower-precision arithmetic. Compare readings around 3000 with a
spread of 0.5 in `float` and `double`.

<Solution>

$E[x^2] \approx 9{,}000{,}000$ and $E[x]^2 \approx 9{,}000{,}000$, while the variance is about 0.25.
Those are seven-digit quantities. Java `double` has roughly 15–16 decimal digits, so this particular
example still resolves the variance well. A `float` has only about seven decimal digits, so subtracting
the two large terms can erase it. Even `double` becomes vulnerable when the mean is much larger relative
to the spread. Welford is the stable default because it never forms that large, nearly equal subtraction.

</Solution>

</Exercise>

<Exercise title="The two deltas">

`delta` uses the mean from *before* the update and `delta2` the mean from *after*. That asymmetry is
not a typo — it is what makes the recurrence exact. Verify it on three samples by hand against the
textbook variance formula.

</Exercise>

For five stationary readings `49.8, 50.1, 50.0, 50.2, 49.9 cm`, the mean is `50.0 cm` and the population
standard deviation is about `0.14 cm`. That small hand check tells you what the running code's two
numbers mean before you collect 200 samples.

A large `std` means aggressive smoothing (or a Kalman filter) is justified; a small one means a light
touch will do. Whatever it comes out to is also what a Kalman filter's $R$ has to be sized against.
Measure it once per sensor and per mounting; do not copy a number out of a lesson. With the noise quantified, the simplest effective filter is next: the low-pass.
