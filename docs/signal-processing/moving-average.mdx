# Moving Average

<Difficulty level="Easy" />

<Abstract>
A moving average smooths a signal by averaging the last N readings equally — excellent at suppressing
random noise, but sluggish to react and easily dragged off by a single outlier. This lesson examines
both failure modes and uses them to motivate the smarter estimator that follows.
</Abstract>

The moving average is the filter you already use intuitively — a "7-day average," a "50-day stock
average." It is excellent at one job and instructively bad at another, which sets up why a smarter
estimator is eventually required.

<Problem title="Steady jitter needs averaging; bursts and lag do not forgive it">

A signal buried in steady random jitter is best cleaned by averaging — but a simple average over *all*
history can never track a moving signal. The fix is a **sliding window**: average only the most
recent N readings, discarding the oldest as each new one arrives. The window size is a direct
smooth-versus-responsive trade-off, and — as the demo will show — a single outlier contaminates the
output for the full N samples.

<Analogy>
<strong>You have seen this.</strong> A rolling case count, a moving stock average, your phone's
average step count — all sliding-window averages that turn a spiky series into a readable trend.
</Analogy>

</Problem>

<Theory title="The average of a sliding window">

Hold the last N readings; report their mean. Next loop, the window slides one step forward.

$$
\hat{x}_k = \frac{1}{N}\sum_{i=0}^{N-1} z_{k-i}
$$

It is a close cousin of the low-pass filter, with a different memory model:

| | Moving average | Low-pass (EMA) |
|---|---|---|
| Remembers | last N readings, **equally** | all readings, **fading** |
| Storage | N values | one number |
| Setting | window size N | smoothing α |
| Best at | killing steady jitter | cheap real-time smoothing |

The cleanest way to *see* that difference in memory is to feed both filters one wild outlier and
watch what the output does afterwards:

<WindowVsFadeExplorer />

This Desmos-style graph is each filter's **impulse response**: which is nothing more than its weight
function, replayed in time. The moving average gives the spike a weight of exactly $1/N$ for exactly
$N$ samples, then drops it entirely: full poison, then total amnesia, with the hard edge at $k = N$.
The EMA takes a *bigger* first hit ($\alpha > 1/N$ for typical settings) but fades it geometrically —
a long, soft tail instead of a cliff. Grow $N$ and the moving average's contamination gets shallower
but *longer*; there is no setting that makes it short *and* shallow. That fixed $N$-sample dwell is
the "single outlier contaminates the output for the full window" failure from the introduction, now
quantified.

The demo below runs the window on a live signal — truth, sensor, and the windowed average. Grow N for
smoothness, then run the step test to feel the lag a large window costs.

<Callout type="warn" title="The two failure modes.">
With a large window the step test ramps up slowly instead of snapping — pure lag. And a single wild
spike shifts the average for the full N samples. For fast-moving or spike-prone data, the Kalman
filter (two lessons ahead) is dramatically better.
</Callout>

</Theory>

<Deploy title="A fixed-cost ring buffer">

On a Control Hub, implement the window as a ring buffer with a running sum, so each update is O(1)
regardless of N. The cost to weigh against the low-pass is the N-value memory.

<JavaCode league="FTC" label="Moving average in constant time">{`private final double[] buffer = new double[N];
private int index;
private int count;
private double sum;

double update(double reading) {
    sum -= buffer[index];      // drop the sample that is now N loops old
    buffer[index] = reading;
    sum += reading;

    index = (index + 1) % buffer.length;
    count = Math.min(count + 1, buffer.length);

    return sum / count;        // count, not N, until the window fills
}`}</JavaCode>

<Exercise title="Trace the ring buffer">

The trick is that the slot you are about to overwrite holds exactly the sample that is now $N$ loops
old, so one subtraction and one addition keep the running sum exact. Work through $N = 4$ with readings
`1, 2, 3, 4, 5, 6` and write down `buffer`, `index`, `sum` and the returned average at every step. Then
answer the second question: what does the average read on loop 2 if you divide by `N` instead of
`count`, and where did those zeros come from?

<Solution>

The averages are `1, 1.5, 2, 2.5, 3.5, 4.5`. On loop 5 the reading `1` leaves the window and the sum
jumps from 10 to 14 in one subtraction. Dividing by `N` on loop 2 gives `0.75` instead of `1.5`: the
two untouched slots still hold their initial zeros, and those zeros are not measurements. `count`
exists so the filter is honest before the window has filled.

</Solution>

</Exercise>
