# Complementary Filter

<Difficulty level="Medium" />

<Abstract>
This is where the module switches from filtering to fusion. A filter cleans one sensor; fusion
combines two sensors whose failures point in opposite directions. The complementary filter is the
simplest fusion there is — one blending constant — shown here on a real FTC pairing: a motor encoder
that is fast but slips away from the truth, and an absolute encoder that does not accumulate relative
motion error but still needs calibration and can be biased, noisy, and slow.
</Abstract>

The previous filters cleaned a *single* sensor, and they all paid the same price: smoothing fights
jitter but does nothing about drift. No amount of averaging fixes a sensor whose *center* is walking
away from the truth. For drift you need a second sensor — one that never walks — and a rule for
combining the two.

<Problem title="The motor encoder is fast but lies slowly; the absolute encoder is honest but rough">

Put an arm on a robot and you usually have two ways to measure its angle:

- **Motor encoder**: counts ticks at the motor, fresh every loop, fine resolution. But it measures
  *the motor*, not the joint. Every bit of belt slip, chain skip, and gear backlash between the two
  accumulates, so the angle you compute from ticks drifts away from the true arm angle over a match.
  Excellent short-term, wrong in the long run.
- **Absolute encoder on the joint**: reads the joint angle itself, so relative-motion error does not
  accumulate. It still needs calibration and can carry a fixed bias; it is noisy and may update slower
  than your loop. Anchored in the long run, rough right now.

Run on the motor encoder alone and the arm slowly forgets where it is. Run on the absolute encoder
alone and your control loop chews on noise. The two failures are opposites — *complementary* — which
is the whole trick.

</Problem>

<Theory title="Predict, then correct on the angle circle">

First predict from the motor encoder's relative motion. Then correct toward the absolute sensor through
the shortest angular innovation:

$$
\begin{aligned}
\theta^-_k &= \operatorname{wrap}(\hat\theta_{k-1}+\Delta\theta_{\text{motor}}),\\
r_k &= \operatorname{wrap}(\theta_{\text{abs}}-\theta^-_k),\\
\hat\theta_k &= \operatorname{wrap}\!\left(\theta^-_k+(1-\alpha)r_k\right).
\end{aligned}
$$

<Formula>
  estimate = prediction + (1 − <Amber>α</Amber>)·wrapped innovation
</Formula>

The prediction advances by the motor motion immediately. The correction gently pulls it toward the
absolute reading. Without the inner wrap, a prediction of $359°$ and a measurement of $1°$ would blend
through the long $358°$ route. $\alpha$ sits close to 1: mostly ride the motor encoder while the absolute
sensor slowly removes accumulated relative error.

The live experiment below uses that exact update. Increase slip, then absolute-sensor noise, and decide
which source each failure should make you trust less.

### Optional derivation: why the frequency paths complement

Away from the angle-wrap seam, small perturbations follow a linear sampled model. In that local,
small-signal regime, the equivalent filters are

$$
H_\text{abs}(z)=\frac{1-\alpha}{1-\alpha z^{-1}},\qquad
H_\text{rel}(z)=\frac{\alpha(1-z^{-1})}{1-\alpha z^{-1}}.
$$

This graph evaluates those exact discrete responses for that linearized behavior; a discontinuous wrap
at the seam is intentionally outside a frequency-response model. The rose curve is the absolute encoder's
**low-pass**: it passes the slow, honest angle and rejects the fast noise. The teal curve is the
motor encoder's **high-pass**: it passes fast motion and blocks slow drift. Their **complex** values sum
to one; their magnitudes generally do not because the paths carry phase. The sweep stops at the sampled
system's Nyquist frequency $1/(2\Delta t)$ and computes the discrete crossover directly.

<Callout type="tip" title="Two wrongs make a right.">
Let it run: the motor-encoder line slides off the truth while the absolute line is fuzzy — yet the
fusion stays smooth <em>and</em> locked on. The compute cost is only a few arithmetic operations and
three angle wraps per loop.
</Callout>

</Theory>

<Deploy title="One line per loop">

The fast source enters as a *delta* (ticks moved since last loop), the honest source as an *absolute*
reading. Seed the estimate from the absolute sensor so the filter starts true:

<JavaCode league="FTC" label="Fuse a motor encoder with an absolute encoder">{`private static final double TAU = 0.5;    // fusion time constant, seconds
private static final double RAD_PER_TICK = 2 * Math.PI / TICKS_PER_REV;

private double angle;        // seed from the absolute encoder, not from zero
private double lastTicks;

double update(double ticks, double absRad, double dt) {
    double alpha = Math.exp(-dt / TAU);        // loop-rate independent

    double delta = (ticks - lastTicks) * RAD_PER_TICK;
    lastTicks = ticks;

    double prediction = wrap(angle + delta);
    double innovation = wrap(absRad - prediction);
    angle = wrap(prediction + (1 - alpha) * innovation);
    return angle;
}`}</JavaCode>

<Exercise title="Both extremes of alpha">

Work out both ends before choosing $\tau$. With $\alpha = 1$ the innovation is ignored entirely — which
sensor are you now using? With $\alpha = 0$ the prediction is discarded — which one now?

<Solution>

$\alpha = 1$ leaves `angle = prediction`, so you are running on the motor encoder alone: smooth, and
drifting forever. $\alpha = 0$ leaves `angle = absRad`, so you are running on the absolute encoder
alone: honest, and jittering every loop. $\tau$ picks where between those you sit, and it picks it in
seconds rather than in loops.

</Solution>

</Exercise>

<Exercise title="Why every line wraps">

All three quantities are angles, and the absolute encoder rolls over. Trace a fusion across the wrap
point with the `wrap` calls removed, and find the exact loop where the estimate jumps by $2\pi$.

<Solution>

The break is in `innovation`. With the mechanism just past $\pi$, `absRad` has rolled to just above
$-\pi$ while `prediction` is still just below $+\pi$. Unwrapped, their difference is about $-2\pi$
instead of the true near-zero, so the filter concludes it is a full turn wrong and drags `angle`
backwards on the very first loop after the rollover.

</Solution>

</Exercise>

Read the last three lines as a sentence: assume the relative sensor was right, measure how far that has
drifted from the absolute one, then walk back a fraction of the way. Fast motion rides on the motor
encoder; slow drift gets pulled out by the absolute reading.

:::note[The drone-textbook version]
Most textbooks teach this filter on a gyro + accelerometer pair: integrate the gyro's rate (fast,
drifts), anchor with the accelerometer's gravity direction (honest, shaky). Same math, different
sensors — and on FTC your IMU already does that fusion internally. The pattern is worth recognizing
in general: *any* fast-relative source plus *any* slow-absolute source fits, like a gyro heading
anchored by an occasional vision bearing.
:::

The complementary filter hand-picks a fixed blend $\alpha$. The Kalman filter computes the
*optimal* blend automatically, every step, from the actual uncertainties — the subject of the next
page.

</Deploy>
