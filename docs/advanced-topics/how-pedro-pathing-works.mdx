# How Does Pedro Pathing Work?

<Difficulty level="Hard" />

<Abstract>
Pedro Pathing is best understood as a reactive path follower: it continuously measures the robot pose,
finds where that pose belongs on a curve, and combines several correction vectors into a drive command.
This page connects the public Pedro documentation and the supplied second-order GVF paper to the FTC
mental model: projection, path progress, cross-track correction, centripetal feedforward, heading
control, and completion logic.
</Abstract>

## Builder checkpoint: four vectors, then tune by symptom

This page is an **architecture explainer**, not drop-in Pedro source. Each loop can be understood as four
jobs combined before mecanum mixing:

| Component | Physical job | FTC symptom if wrong or missing |
|---|---|---|
| Tangential drive | move forward along the curve | robot corrects but crawls or stalls |
| Attractive correction | pull and damp motion back toward the curve | robot stays displaced or snakes after a bump |
| Centripetal feedforward | anticipate inward acceleration on bends | robot runs wide only on fast curves |
| Heading correction | track orientation independently | position is right but the robot faces wrong |

| Symptom on the robot | Check first in the official workflow |
|---|---|
| Pose axes/scale drift before following | [localization setup](https://pedropathing.com/docs/pathing/tuning/localization) |
| Straight paths oscillate or recover lazily | translational follower tuning |
| Fast curves run wide but slow curves work | centripetal correction and velocity constraints |
| Heading oscillates while translation is clean | heading controller tuning |
| The robot reaches the end but stays busy | completion constraints and terminal velocity |

Use Pedro's maintained [localization](https://pedropathing.com/docs/pathing/tuning/localization) and
[tuning sequence](https://pedropathing.com/docs/pathing/tuning) before changing internals. If you can name
the four jobs and choose the first tuner from a symptom, a builder may stop here. The remaining calculus
and whitepaper notation are optional architecture/audit depth.

## The FTC problem Pedro is solving

Pure Pursuit chases a point ahead of the robot. That is intuitive, but it has a weakness: when the
robot is disturbed, the follower is always negotiating between "catch the moving target" and "get back
onto the path." Pedro's public documentation describes a different goal: follow Bezier curves while
maintaining speed, consistency, and correction for disturbances.

The clean way to think about it is this:

1. The path is not just a list of waypoints. It is a smooth curve.
2. The robot estimates its current pose from localization.
3. The follower projects the robot onto the curve to find the closest or most relevant path parameter.
4. It computes correction vectors around that point.
5. It converts the desired field motion into mecanum drive power.

That is why Pedro feels more "reactive" than a precomputed trajectory. The follower is not blindly
replaying a timed script; it keeps asking, "Given where the robot actually is, what field should pull it
back onto the path and keep it moving forward?"

The picture below is the first-order idea. Each arrow says where a robot would like to move if it were
currently at that field position. Near the path, the arrow points mostly along the curve. Far from the

The second-order Pedro paper takes this idea one level deeper. Instead of treating the field as only a
desired velocity direction, it builds a field over pose plus velocity. The follower therefore cares
about more than where the robot is: it also tracks how fast the robot is already moving, and whether it
must brake, curve, or correct heading.

## Optional architecture derivation

### The path is a curve, not a waypoint list

Pedro uses smooth curves, commonly Bezier-style path primitives. A generic path can be written as

$$
\phi(t) =
\begin{bmatrix}
x(t) \\
y(t)
\end{bmatrix},
\qquad 0 \le t \le 1
$$

<EquationLegend
  items={[
    {symbol: '\u03c6 (phi)', meaning: 'the PATH itself, as a function. Feed it a parameter and it hands back a point'},
    {symbol: 't', meaning: 'the path parameter, running 0 to 1 from start to end. It is not time and not distance: t = 0.5 is not the halfway point by length'},
    {symbol: '\u03c6\u2032(t)', meaning: 'the derivative with respect to t: which way the path is heading there, with a length that depends on how fast t sweeps the curve'},
  ]}
/>

where:

- $\phi(t)$ is the point on the path at parameter $t$.
- $x(t)$ is the field x-coordinate of that point.
- $y(t)$ is the field y-coordinate of that point.
- $t$ is progress along this path segment, with $t = 0$ at the start and $t = 1$ at the end.

The tangent direction is

$$
\hat{\mathbf{T}}(t) = \frac{\phi'(t)}{\|\phi'(t)\|}
$$

where:

- $\phi'(t)$ is the derivative of the path position with respect to $t$.
- $\|\phi'(t)\|$ is the length of that derivative vector.
- $\hat{\mathbf{T}}(t)$ is the unit tangent, meaning the "forward along the curve" direction.

Once the path is a curve instead of a waypoint list, you can ask for its tangent, curvature, distance
remaining, and desired heading at any point.

### Projection: which point of the curve the robot belongs to

Let the robot's current field position be

$$
\mathbf{p} =
\begin{bmatrix}
p_x \\
p_y
\end{bmatrix}
$$

<EquationLegend
  items={[
    {symbol: 'p', meaning: 'the robot\u2019s current field position, as a vector. Its components p_x and p_y are just its x and y'},
    {symbol: 'T\u0302(t)', meaning: 'the UNIT tangent. Dividing \u03c6\u2032 by its own length throws away the parameterization speed and keeps only direction'},
  ]}
/>

The follower needs the path parameter that best corresponds to the robot's current position. The paper
writes this as a closest-point problem:

$$
D(t) = \frac{1}{2}\|\phi(t) - \mathbf{p}\|^2
$$

<EquationLegend
  items={[
    {symbol: 'D(t)', meaning: 'half the squared distance from the robot to the path point at t. Not the braking distance D(v) further down the page'},
    {symbol: 'the one-half and the square', meaning: 'both are conveniences. Squaring removes the square root, and the half cancels when you differentiate. Whatever t minimizes this also minimizes true distance'},
  ]}
/>

where:

- $D(t)$ is the squared distance from the robot to the path point $\phi(t)$.
- $\mathbf{p}$ is the robot position.
- The factor $\frac{1}{2}$ does not change the closest point; it just makes the derivative cleaner.

A candidate for the closest point occurs at an endpoint of the segment or where the derivative is zero:

$$
D'(t) = \left(\phi(t) - \mathbf{p}\right) \cdot \phi'(t) = 0
$$

That dot product has a geometric meaning. At an *interior* closest point, the vector from the path to
the robot is perpendicular to the path tangent. Because $D'(t) = 0$ is necessary but not sufficient —
it also marks local *maxima* of distance — the follower takes the global minimum among the interior
candidates and the two endpoints. It can use the previous loop's parameter as a seed, because in a
normal FTC loop the robot cannot teleport from one part of the curve to another.

Drag the robot below. The green point is $\phi(\psi(\mathbf{p}))$: the path point the follower currently
believes is closest to the robot. The yellow arrow is the tangent direction used for forward motion, and
the blue arrow is the normal direction used for correction.

<PathProjection />

<Callout type="idea" title="Projection is the hidden building block.">
Projection is what makes every later term local. Once the follower knows "the robot belongs near this
point on the curve," each correction can be computed from that one neighborhood: tangent, normal,
curvature, heading target, and remaining distance.
</Callout>

### Cross-track error and its damped spring

Define the positional error used in the paper:

$$
\mathbf{e}_p = \phi(\psi(\mathbf{p})) - \mathbf{p}
$$

<EquationLegend
  items={[
    {symbol: '\u03c8(p) (psi)', meaning: 'the PROJECTION: given the robot at p, which path parameter t is closest. It is the answer to the minimization just above'},
    {symbol: 'e_p', meaning: 'the positional error VECTOR, pointing from the robot to its closest point on the path'},
  ]}
/>

where:

- $\psi(\mathbf{p})$ is the path parameter associated with the robot position.
- $\phi(\psi(\mathbf{p}))$ is the closest path point.
- $\mathbf{e}_p$ points from the robot back toward that path point.

The attractive term is a spring-like acceleration back toward the curve. A simplified FTC reading is:

$$
\mathbf{a}_{\text{attract}} \approx k_p^t\,\mathbf{e}_p - k_d^t\,\mathbf{v}_{\perp}
$$

<EquationLegend
  items={[
    {symbol: 'k_p^t, k_d^t', meaning: 'proportional and derivative gains for TRANSLATION; the t superscript labels which loop they belong to, and the r superscript later marks the rotational pair'},
    {symbol: 'v_\u22a5', meaning: 'the component of the robot\u2019s velocity PERPENDICULAR to the path: how fast it is drifting sideways. Damping this is what stops the pull-back from oscillating'},
  ]}
/>

where:

- $\mathbf{a}_{\text{attract}}$ is the correction acceleration toward the path.
- $k_p^t$ is the translational proportional gain.
- $k_d^t$ is the translational damping gain.
- $\mathbf{v}_{\perp} = (\mathbf{v} \cdot \hat{\mathbf{N}})\,\hat{\mathbf{N}}$ is the component of robot
  velocity along the path normal $\hat{\mathbf{N}}$ (positive when the robot is moving away from the
  path), so the damping term opposes that motion.

The exact paper expression is more careful about singular cases and dot products, but this is the
physical story: if the robot is off the curve, push it back; if it is already moving back too
aggressively, damp it.

### Leaning into a bend before the robot drifts

A robot on a curved path needs inward acceleration even if it has zero cross-track error. Without that
term, it tends to cut wide or rely on feedback after it is already off the path.

For a curve with curvature $\kappa$, the required normal acceleration is

$$
a_c = v^2 \kappa
$$

<EquationLegend
  items={[
    {symbol: 'a_c', meaning: 'the CENTRIPETAL acceleration a curve of curvature \u03ba demands at speed v. Nothing supplies it for free; the drivetrain must produce it', unit: 'in/s\u00b2'},
  ]}
/>

where:

- $a_c$ is centripetal acceleration.
- $v$ is speed along the path tangent.
- $\kappa$ is curvature, equal to $\frac{1}{R}$ for a circle.
- $R$ is the radius of the turn.

Drag the points below. Tighter curvature means smaller radius, larger $\kappa$, and more required inward
acceleration for the same speed. (The demo fits a circle through three *separate* points — the Menger
curvature — so it equals a path's true local curvature only in the limit as the points coincide; drag
them close together to approximate the curvature at a single point.)

<CurvatureCircle />

The paper writes the centripetal component in the language of the path:

$$
\xi_C(x) =
k_c
\left(
\operatorname{comp}_{\hat{\mathbf{T}}}( \mathbf{v} )
\right)^2
\frac{\hat{\mathbf{T}}'(\psi(\mathbf{p}))}{\|\phi'(\psi(\mathbf{p}))\|}
$$

<EquationLegend
  items={[
    {symbol: '\u03be (xi)', meaning: 'the paper\u2019s name for one component of its vector field. \u03be_C is the centripetal part, \u03be_P the positional, \u03be_R the rotational'},
    {symbol: 'k_c', meaning: 'the centripetal gain, tuning how strongly the follower leans into a bend'},
    {symbol: 'comp_T\u0302(v)', meaning: 'the COMPONENT of velocity along the tangent: how fast the robot is moving along the path rather than across it. Squaring it is the v\u00b2 of the line above'},
    {symbol: 'T\u0302\u2032 / \u2016\u03c6\u2032\u2016', meaning: 'how fast the tangent is turning per unit of DISTANCE rather than per unit of t. That ratio is curvature, written without naming it'},
  ]}
/>

where:

- $\xi_C(x)$ is the centripetal acceleration component of the field.
- $x$ is the full robot state, including pose and velocity.
- $k_c$ is a tunable scale factor absorbing robot-specific effects.
- $\operatorname{comp}_{\hat{\mathbf{T}}}(\mathbf{v})$ is the scalar component of robot velocity along
  the tangent direction.
- $\hat{\mathbf{T}}'$ measures how quickly the tangent direction changes along the curve.
- $\|\phi'\|$ converts parameter-rate curvature into distance-rate curvature.

If the path is bending and the robot is already moving fast along it, the follower applies an
anticipatory sideways correction before the robot has drifted.

### Tangential speed from a measured braking model

The follower also needs to decide how much to push along the tangent. The paper uses remaining path
distance:

$$
d =
\int_{\psi(\mathbf{p})}^{1}
\|\phi'(s)\|\,ds
$$

<EquationLegend
  items={[
    {symbol: 'd', meaning: 'the arc length still remaining, from where the robot projects onto the path to the end'},
    {symbol: '\u2016\u03c6\u2032(s)\u2016 ds', meaning: 'the standard arc-length integral. Because equal steps in the parameter are not equal steps in distance, you have to integrate the speed of the parameterization to get real length'},
    {symbol: 's', meaning: 'a dummy integration variable sweeping the parameter, not the robot\u2019s speed'},
  ]}
/>

where:

- $d$ is remaining arc length along the path.
- $s$ is a dummy integration variable.
- $\psi(\mathbf{p})$ is the robot's current projected path parameter.
- $\|\phi'(s)\|$ converts parameter change into physical distance.

The paper writes the speed limit as $v_{\text{desired}} = \sqrt{2ad}$ — constant-deceleration
kinematics. That form is deliberate: the algorithm is meant to work in any number of dimensions, so
the paper does not commit to one drivetrain's physics. The shipped follower does something better. It
**measures** how the robot actually stops.

A real drivetrain braking is not a constant-deceleration object. The motors brake through back-EMF,
which fades as the robot slows, and the drivetrain drags on itself through viscous friction. Fit
braking distance against entry speed on a real robot and you get a quadratic with a linear term:

$$
D(v) = a v^2 + b v
$$

<EquationLegend
  items={[
    {symbol: 'D(v)', meaning: 'how far the robot ACTUALLY takes to stop from speed v, fitted on a real robot rather than derived'},
    {symbol: 'a', meaning: 'the quadratic coefficient, capturing ideal constant-deceleration braking'},
    {symbol: 'b', meaning: 'the linear coefficient, capturing what constant deceleration misses: viscous drag and the drivetrain fighting itself. Measure both; they are properties of your robot'},
  ]}
/>

where:

- $D(v)$ is how far the robot travels before stopping, entering at speed $v$.
- $a$ captures the inertia-versus-braking-torque part (this is what constant-deceleration kinematics
  approximates as $\frac{1}{2a_{\text{decel}}}$).
- $b$ captures the speed-proportional losses: back-EMF braking and viscous drag. On Pedro's test data
  it lands in the hundredths. Small, but load-bearing — leave it out and the model misses short stops.

The braking-distance regression data behind this comes from Pedro Pathing, collected by Jacob Ophoven.

There are two ways to use the fit:

- **The Pedro 2.1.x form** (introduced in v2.1.0) runs a position controller and simply subtracts the
  braking distance from the error:
  $e = \lVert \mathbf{x}_{\text{target}} - \mathbf{x} \rVert - D(v)$. When the remaining distance
  equals the stopping distance, the error reads zero and the controller stops pushing.
- **Inverting the fit**, described in the whitepaper as future work. Given remaining distance $d$,
  solve $a v^2 + b v = d$ with the quadratic formula and keep the larger root:

$$
v_{\text{desired}} = \frac{-b + \sqrt{b^2 + 4ad}}{2a}
$$

  then track that speed with a velocity PID. Same fit, used as a speed plan instead of an error offset.
  In v2.1.2 this form was not in the released library: the whitepaper described inverting $D(v)$ to
  recover a target speed, while that release used the error-offset controller above.

:::warning[The coefficients depend on how you brake]
Pedro brakes actively, at roughly $-0.2$ motor power. A driver who lets go of the sticks brakes at
zero power and coasts farther. The $D(v) = av^2 + bv$ model holds either way, but the fitted $a$ and
$b$ do not transfer between braking styles. Refit for the behavior you actually use.
:::

<Admonition type="tip" title="Why this feels different from fixed motion profiles">

A timed trajectory decides speed as a function of planned time. A reactive follower can decide speed as
a function of measured progress. If the robot gets bumped or slips, the follower still computes distance
remaining from where the robot actually is.

</Admonition>

### Heading runs on its own controller

FTC autos often need to move one direction while facing another: intake while strafing, score while
rotating, or approach a stack with a fixed camera angle. Pedro's docs describe heading control as part of
the path-following behavior, and the paper models the target heading as a smooth interpolation:

$$
\theta(t)
$$

where:

- $\theta(t)$ is the desired robot orientation at path parameter $t$.
- For FTC in the plane, this is usually a single heading angle.
- In the paper's general setting, it lives in $SO(n)$, the space of rotation matrices.

For FTC, you can read the rotational correction as the familiar heading loop:

$$
\alpha_{\text{cmd}}
=
k_p^r\,\operatorname{wrap}(\theta(\psi(\mathbf{p})) - \theta_{\text{robot}})
- k_d^r\,\omega
$$

<EquationLegend
  items={[
    {symbol: '\u03b1_cmd', meaning: 'the commanded angular acceleration. Here \u03b1 is a rotational command, not the filter blend factor used in signal processing'},
    {symbol: 'k_p^r, k_d^r', meaning: 'the ROTATIONAL gain pair, separate from the translational ones above'},
    {symbol: '\u03b8(\u03c8(p))', meaning: 'the target heading at the robot\u2019s projected point: read the projection first, then look up what heading the path wants there'},
  ]}
/>

where:

- $\alpha_{\text{cmd}}$ is commanded angular acceleration or rotational correction.
- $k_p^r$ is the heading proportional gain.
- $k_d^r$ is the heading damping gain.
- $\theta_{\text{robot}}$ is the measured robot heading.
- $\omega$ is measured angular velocity.
- `wrap` maps the angle error into the shortest equivalent angle.

The important architecture point is separation. Translation can follow the curve while heading follows
its own interpolation.

The four-vector checkpoint at the top is now fully specified: projection supplies a regular unit tangent,
signed curvature selects the side of centripetal correction, remaining distance slows the endpoint, and
heading remains its own wrapped controller. The final command still passes through
[Mecanum Kinematics](../path-following/mecanum-kinematics.mdx).

## Implementation shape

The exact Pedro implementation has its own classes, tuners, and APIs. A clean FTC architecture inspired
by the same decomposition would look like this:

<JavaCode league="FTC" label="Pedro-style follower decomposition">{`void startPath() {
    lastT = 0;
    timer.reset();
}

MoveStatus update(PoseSample sample) {
    Pose2d pose = sample.pose();
    Vector2d velocity = sample.fieldVelocity();

    lastT = path.project(pose.vec(), lastT);     // seeded from last loop

    MoveStatus completion = moveStatus(sample, path.endPose(), timer);
    boolean atEnd = lastT >= 1 - TERMINAL_TOL;
    if (completion == TIMED_OUT || (completion == REACHED && atEnd)) {
        drive(0, 0, 0);
        return completion;
    }

    Vector2d tangent = path.tangent(lastT).unit();
    Vector2d leftNormal = new Vector2d(-tangent.y(), tangent.x());
    double signedCurvature = path.curvature(lastT);   // + left, - right bend
    double remaining = path.remainingArcLength(lastT);

    double tangentSpeed = velocity.dot(tangent);
    double brakingSpeed = Math.sqrt(2 * MAX_DECEL * remaining);
    double endScale = clamp(remaining / END_SLOWDOWN_DISTANCE, 0, 1);
    double desiredSpeed = Math.min(CRUISE_SPEED, brakingSpeed) * endScale;

    Vector2d alongPath = tangent.times(
            DRIVE_KP * (desiredSpeed - tangentSpeed));
    Vector2d towardPath = path.position(lastT).minus(pose.vec())
            .times(TRANSLATION_KP);
    Vector2d centripetal = leftNormal.times(
            CENTRIPETAL_K * tangentSpeed * tangentSpeed * signedCurvature);

    Vector2d fieldCommand = alongPath.plus(towardPath).plus(centripetal);
    double turn = HEADING_KP * wrap(path.heading(lastT) - pose.heading());

    driveFieldCentric(fieldCommand, turn);
    return RUNNING;
}
`}</JavaCode>

If the tangent's length is near zero the path has a cusp: stop and fail loudly rather than normalizing a
zero vector. The three vectors each have one job — close the loop on speed *along* the path, pull back
*onto* the path, and lean into the bend before drifting out of it.

<Exercise title="Delete each vector in turn">

The decomposition is the lesson. Each vector can be tuned alone and switched off to see what it was
doing. Work out what the robot does with each of the three deleted.

<Solution>

Without `alongPath` nothing regulates speed: the robot still converges to the path and still points
the right way, but it crawls or overruns depending only on the other two terms, and the braking plan
does nothing.

Without `towardPath` there is no correction for lateral error: push the robot off the line and it
happily continues parallel to the path forever, because tangent speed and curvature are both still
satisfied.

Without `centripetal` the robot enters every bend on the old tangent and drifts wide, then
`towardPath` yanks it back — so corners are cut on the outside and the path is tracked with a
characteristic lag that gets worse the faster you go.

</Solution>

</Exercise>

<Exercise title="Heading as a scalar, and the squared speed">

Work out why heading is a separate scalar rather than a fourth vector. What kind of drivetrain does that
assume, and what would change on a differential drive? Then work out why the centripetal term uses
`tangentSpeed` *squared* and the *signed* curvature — which of the two decides the size of the lean,
and which decides its direction?

<Solution>

Separating heading assumes a holonomic drivetrain, where translation and rotation are independent
commands. On a differential drive they are not: heading *is* how you translate, so the follower has to
solve for a curvature the chassis can actually execute rather than adding a turn on top.

For the centripetal term, required centripetal acceleration is $v^2\kappa$ — the squared speed sets
the magnitude, which is why the lean grows quadratically as you speed up, and the sign of $\kappa$
sets which side of the path to lean toward.

</Solution>

</Exercise>

<Admonition type="warning" title="This is architecture, not drop-in Pedro source">

The snippet shows the decomposition, not the exact Pedro Pathing implementation. It deliberately uses one
testable convention: a normalized tangent, its fixed **left** normal, and signed curvature. A positive
left bend therefore commands left/inward acceleration; negative curvature reverses that vector for a
right bend. It never chooses an already-inward normal and then multiplies it by a sign that could flip it
outward. Real teams still need the official localization/tuning flow and the library's own constraints.

</Admonition>

## What completion really means

A path is not "done" just because $t$ reaches one. A reliable follower checks several kinds of completion:

- path progress is at or near the end;
- position error is small enough;
- heading error is small enough;
- velocity has settled enough for the next action;
- a timeout or correction window has elapsed.

Pedro's docs describe completion constraints around `follower.isBusy()`. The architecture sketch tapers
speed over the terminal distance, then uses the shared `MoveStatus`: both `REACHED` and `TIMED_OUT` stop
the drive, while only `REACHED` advances autonomous policy normally. If you transition too early, the
next mechanism action begins while the robot is still correcting; too late wastes match time.

## What the second-order field adds

The supplied paper, *Second-Order Multidimensional Guiding Vector Field for Parametric Path-Following
Under Holonomic Constraints*, gives the theoretical version of this architecture. The big contribution is
not merely "draw arrows around a path." It defines a smooth second-order vector field over the robot's
configuration and velocity state:

$$
\xi(x) = (v, R\Omega, \xi_P(x), \xi_R(x))
$$

<EquationLegend
  items={[
    {symbol: 'x', meaning: 'the full CONFIGURATION AND VELOCITY state, not just position. This is why the paper calls the field second-order'},
    {symbol: 'R\u03a9', meaning: 'the rotational part of the state: the robot\u2019s orientation R together with its angular velocity \u03a9'},
    {symbol: '\u03be_P, \u03be_R', meaning: 'the positional and rotational components of the field. The next equation is exactly this line in plain English'},
  ]}
/>

where the tuple is the commanded time-derivative of the state $x = (\mathbf{p}, R, \mathbf{v}, \Omega)$
(position, rotation, translational velocity, angular velocity):

- $\xi(x)$ is the complete second-order guiding vector field, i.e. the commanded state derivative
  $(\dot{\mathbf{p}}, \dot{R}, \dot{\mathbf{v}}, \dot{\Omega})$.
- $v$ is translational velocity, so $\dot{\mathbf{p}} = v$.
- $R\Omega$ is the rotational kinematics term, where $\Omega$ is the skew-symmetric angular-velocity
  matrix and $\dot{R} = R\Omega$.
- $\xi_P(x)$ is the translational acceleration component $\dot{\mathbf{v}}$.
- $\xi_R(x)$ is the rotational acceleration component $\dot{\Omega}$.

For an FTC mecanum robot, the friendly version is:

$$
\begin{gathered}
\text{next command}
=
\text{drive along}
+ \text{pull back} \\[2pt]
+ \text{curve feedforward}
+ \text{turn to heading}
\end{gathered}
$$

Each term in that sum is one of the four jobs from the checkpoint table, and each carries its own
constants: $k_p^t$ and $k_d^t$ for the pull back, $k_c$ for the curve feedforward, $k_p^r$ and $k_d^r$
for heading, and the fitted $D(v)$ for the drive-along speed. Those are the numbers a team actually
tunes.
