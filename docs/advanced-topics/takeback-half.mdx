# Take-Back-Half

<Difficulty level="Medium" />

<Abstract>
Bang-bang gets a flywheel back up to speed quickly but never settles. <strong>Take-back-half</strong>
(TBH) is a small change: add up the error like an integral, and every time the error changes sign, cut
the output back halfway toward where it was the last time that happened. With a sensible gain, the
flywheel settles on a steady speed and still recovers quickly after a shot. It has one gain to tune.
</Abstract>

<Admonition type="note" title="Read first">

This builds on [Bang-Bang Control](../control-theory/bang-bang.mdx), which explains why a heavy
flywheel suits an on/off controller and why plain bang-bang keeps rippling around the target.

</Admonition>

<Theory>

## Settling without losing the fast recovery

Take-back-half keeps a running output, `drive`, and adds a little to it every loop in proportion to the
error, like an integral term. When the flywheel is slow, `drive` climbs. When it overshoots, `drive`
starts falling.

The trick happens each time the speed crosses the target. Crossing means you've gone too far, so set
`drive` to the average of its current value and its value at the *previous* crossing.

Try it with numbers. Say the power that would hold the target speed exactly is 0.60, but you don't know
that. The flywheel spins up with `drive` climbing, and at the first crossing `drive` has reached 0.80.
There's no previous crossing yet, so remember 0.80. The flywheel overshoots, `drive` drifts down, and at
the next crossing it's at 0.50. Average that with 0.80 to get 0.65, and remember 0.65. Next crossing,
`drive` has drifted to 0.57, and averaging with 0.65 gives 0.61. The values close in on 0.60 from both
sides.

$$
\begin{gathered}
\text{drive} \mathrel{+}= g\,e\,\Delta t \\[3pt]
\text{on a sign change of } e:\quad
\text{drive} \leftarrow \tfrac12\big(\text{drive} + \text{drive}_\text{last-cross}\big)
\end{gathered}
$$

$g$ is the one gain, and $\text{drive}_\text{last-cross}$ is `drive` at the previous crossing.

In the demo, the green trace is TBH. It recovers almost as fast as bang-bang on the way up, then stops
rippling and holds a flat speed, while bang-bang (red) keeps switching.

<BangBang />

<Callout type="idea" title="Why halfway?">
When the flywheel is below the target, the power was too low, and when it's above, the power was too
high, so the right power is somewhere between the values at two crossings. Averaging them splits the
difference, a bit like guessing a number by halving the range each time. It isn't a guarantee, though.
If $g$ is too large, `drive` overshoots so far between crossings that it can keep bouncing instead of
settling, so tune $g$ on the real mechanism.
</Callout>

</Theory>

<Deploy>

## Take-back-half on the Control Hub

<JavaCode league="FTC" label="Takeback-half velocity controller">{`private double drive;         // the current output
private double driveAtZero;   // the output at the last error sign change
private Double lastError;     // null until the first update

double update(double measured, double target, double dt) {
    double error = target - measured;
    drive = clamp(drive + GAIN * error * Math.max(0, dt), 0, 1);

    if (error != 0) {
        if (lastError != null && Math.signum(error) != Math.signum(lastError)) {
            drive = (drive + driveAtZero) / 2;
            driveAtZero = drive;
        }
        lastError = error;
    }
    return drive;
}
`}</JavaCode>

An error of exactly zero is skipped so it can't look like an extra crossing.

<Exercise title="Tracing the crossings">

Sketch a flywheel overshooting, crossing, undershooting, and crossing again. Mark `drive` at each
crossing. Why does averaging bring it closer to the holding power?

<Solution>

At one crossing `drive` is too high, and at the next it's too low, so the holding power is between them.
Averaging lands in the middle of that range, and each new crossing narrows it. The flywheel's own
inertia also smooths the speed between crossings, which helps. With a reasonable gain the output
settles on the power that holds the target speed.

</Solution>

</Exercise>

<Exercise title="Why a flywheel, and why 0 to 1">

A flywheel is heavy, and the motor can push it faster but can only let it coast slower. What would a PID
controller need to handle that, and how many things would you tune? Why is `drive` clamped to
$[0, 1]$ instead of $[-1, 1]$?

<Solution>

A PID would need `kP`, `kI`, `kD`, an I-zone, and anti-windup to cope, several of which affect each
other. TBH needs `GAIN`. The clamp is $[0, 1]$ because negative power would drive the flywheel backwards,
which no shooter wants. The only way to slow down is to stop pushing and let friction do it. Allowing
negative values would let one overshoot brake the wheel hard and cost much more recovery time than
coasting.

The technique came from VEX flywheel control. Comparing its step response with a tuned PI controller on
the same mechanism is a good experiment.

</Solution>

</Exercise>

Starting `driveAtZero` from a [feedforward](../control-theory/feedforward.mdx) estimate helps a lot:
TBH then settles in about one crossing instead of several. Watch the units. $k_V$ is volts per unit of
speed, but `drive` is a power from 0 to 1, so the starting value is $k_V \cdot v_\text{target} / V_\text{bat}$.
For a flywheel with $k_V = 0.02$ at 300 rad/s on a 12 V battery that's $6 / 12 = 0.5$. Forget to divide by
the battery and you get 6.0, six times full power, and TBH starts pinned at the maximum.

</Deploy>
