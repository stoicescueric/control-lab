# On-Bot Control & Dynamic Targeting

<Difficulty level="Hard" />

<Abstract>
Once the projectile model exists, the robot still has to execute it under match conditions: a flywheel loses momentum after every shot, lookup tables can invent fake commands, and a moving chassis changes the aiming geometry. This lesson makes those three deployment problems interactive so the control logic can be inspected instead of trusted blindly.
</Abstract>

The simulator answers "what should the shot be?" The robot has a harder question: "can I make that shot right now?" If the flywheel is not recovered, if interpolation overshoots a calibration shelf, or if the robot aims at the real target while moving sideways, the paper model is technically correct and the shot still misses.

<DynamicTargetingDashboard />

## Core checkpoint: three transferable ideas

The dashboard's first three tabs form the implementable core: recover a disturbed flywheel, interpolate
measured commands without overshoot, and cancel velocity inherited from the chassis. Build and log those
three pieces before considering the research extensions later on this page.

### 1. Recover the flywheel after a shot

A flywheel shot is a disturbance. The projectile leaves with energy that used to be stored in the wheel, so the measured velocity drops. A basic velocity controller tries to recover with error feedback:

$$
u = k_S + k_V r + k_P(r - y)
$$

<EquationLegend
  items={[
    {symbol: 'u', meaning: 'motor command or voltage request', unit: 'V'},
    {symbol: 'r', meaning: 'target flywheel velocity', unit: 'ticks/s or rad/s'},
    {symbol: 'y', meaning: 'measured flywheel velocity', unit: 'ticks/s or rad/s'},
    {symbol: 'k_S', meaning: 'static friction compensation term', unit: 'V'},
    {symbol: 'k_V', meaning: 'velocity feedforward gain', unit: 'V per velocity'},
    {symbol: 'k_P', meaning: 'proportional feedback gain', unit: 'V per velocity error'},
  ]}
/>

The research controller adds an asymmetric recovery mode: if the wheel is below the ready band after a shot, command aggressively upward; if it is above target, do not kick downward with the same violence. That asymmetry matters because a flywheel below target causes a short shot, while a small overspeed can often be absorbed by the calibration margin.

### 2. Keep calibrated lookup tables monotone

Calibration data is sparse. The robot may know good shooter settings at a few distances, but during the match it needs values between those distances. A lookup table stores the measured shots and *interpolates* to fill the gaps — and the choice of interpolant decides whether those in-between values are safe.

<LookupTableIllustration />

A natural cubic spline is smooth, but smooth is not the same as safe. If the data contains a flat shelf, the spline can overshoot between equal points and command a speed that was never measured. The safer choice for monotone data is a monotone cubic Hermite interpolant. First set both endpoint tangents to zero on every interval whose secant slope is zero. On every nonzero interval, initialize tangents with the same sign as the secant, so $\alpha_k \ge 0$ and $\beta_k \ge 0$, then apply the Fritsch-Carlson projection:

$$
\alpha_k^2 + \beta_k^2 \le 9
$$

<EquationLegend
  items={[
    {symbol: '\u03b1_k, \u03b2_k', meaning: 'the two tangent ratios at interval k, each the interval\u2019s end tangent divided by its secant slope. They are not the filter blend \u03b1 used elsewhere on the site'},
    {symbol: 'the secant', meaning: 'the straight line between two consecutive data points. Matching its sign is what keeps the interpolant from overshooting between them'},
    {symbol: '\u2264 9', meaning: 'the Fritsch-Carlson circle. Staying inside it is exactly the condition for the spline to remain MONOTONE, which for a flight-time lookup means further can never mean sooner'},
  ]}
/>

<EquationLegend

    {symbol: 'beta_k', meaning: 'right endpoint tangent normalized by the interval secant slope', unit: 'unitless'},

The dashboard lets you drag calibration knots. The red curve shows what a natural spline can do in a dangerous flat region. The blue curve shows the monotone Hermite alternative staying inside the behavior implied by the data.

### 3. Cancel inherited chassis velocity with a bounded fixed point

When the robot drives while firing, the projectile inherits chassis velocity. The turret should not aim at the real target; it should aim at a virtual target shifted opposite the robot motion during the launch delay and projectile flight. With $\mathbf v_R$ defined as the robot's field-frame chassis velocity, the projectile already inherits $+\mathbf v_R$, so the aim displacement must cancel it:

$$
\mathbf{p}^{(i+1)}_{\text{virtual}}
=
\mathbf{p}_{\text{target}}
-
G\mathbf{v}_{R}\left(t_d + t_f^{(i)}\right)
$$

<EquationLegend
  title="Symbols in the virtual target"
  items={[
    {symbol: 'superscript (i)', meaning: 'the ITERATION number of the fixed-point loop, not a time step. Each pass refines the previous guess'},
    {symbol: 'p_virtual', meaning: 'the fictitious point to aim at, offset from the real target so the shot lands correctly despite the robot\u2019s motion'},
    {symbol: 'v_R', meaning: 'the ROBOT\u2019s field-frame velocity. The projectile leaves already carrying this, which is exactly what the offset has to cancel'},
    {symbol: 't_d', meaning: 'feeder delay: dead time between the command to fire and the projectile actually leaving', unit: 's'},
    {symbol: 't_f', meaning: 'flight time for this iteration\u2019s geometry. It depends on the distance, which depends on the aim point, which is why this must iterate', unit: 's'},
    {symbol: 'G', meaning: 'the motion gain, a scale from 0 to 1 on how much of the robot\u2019s velocity to compensate. Set below 1 when the model overcorrects in practice'},
  ]}
/>

<EquationLegend
  items={[
    {symbol: 'p_virtual', meaning: 'virtual point the turret aims at', unit: 'field position'},
    {symbol: 'p_target', meaning: 'fixed real target location', unit: 'field position'},
    {symbol: 'G', meaning: 'empirical chassis-motion compensation gain', unit: 'unitless'},
    {symbol: 'v_R', meaning: 'robot chassis velocity vector', unit: 'distance/s'},
    {symbol: 't_d', meaning: 'feeder or launch delay before free flight', unit: 's'},
    {symbol: 't_f', meaning: 'projectile flight time from lookup or simulator', unit: 's'},
  ]}
/>

This is circular: the virtual target changes the distance, the distance changes flight time, and flight time changes the virtual target. Fixed-point iteration breaks the loop. Start with the real target, compute a flight time, shift the target, compute the new flight time, and stop when the time changes by less than the tolerance.

The iteration is locally contractive when
$G\lVert\mathbf v_R\rVert\,|dt_f/dd| < 1$; the radial projection can make the actual derivative smaller
still. At ordinary speeds with a gently sloped flight-time table, each pass moves the answer less than
the last, and the dashboard usually converges in two or three rounds. At very high chassis speed, near
an abrupt table slope, or with impossible geometry, that bound can fail even if the table is otherwise
valid. The hard iteration cap therefore protects the real-time loop from non-convergence as well as bad data.

### Core implementation: bound the deployed solver

On the robot the fixed-point loop is explicit and bounded. It runs inside the autonomous control loop, so
even bad data or impossible geometry must return in predictable time.

<JavaCode league="FTC" label="The bounded fixed-point aim solver">{`// Returns a virtual aim point plus CONVERGED / NOT_CONVERGED / INVALID_LOOKUP.
AimSolution solveVirtualTarget(Vector2d shooter, Vector2d target,
                               Vector2d robotVelocity) {
    double flightTime = lookupFlightTime(shooter.minus(target).norm());
    if (!(Double.isFinite(flightTime) && flightTime > 0)) {
        return AimSolution.invalidLookup();
    }

    Vector2d virtual = target;
    for (int i = 0; i < MAX_ITERATIONS; i++) {
        double compensationTime = feederDelay + flightTime;
        virtual = target.minus(
                robotVelocity.times(motionGain * compensationTime));

        double nextTime = lookupFlightTime(shooter.minus(virtual).norm());
        if (!(Double.isFinite(nextTime) && nextTime > 0)) {
            return AimSolution.invalidLookup();
        }
        if (Math.abs(nextTime - flightTime) < tolerance) {
            return new AimSolution(virtual, CONVERGED);
        }
        flightTime = nextTime;
    }
    return new AimSolution(virtual, NOT_CONVERGED);
}
`}</JavaCode>

At the call site, only `CONVERGED` may fire:

<JavaCode league="FTC" label="Refusing to shoot on an unvalidated solution">{`AimSolution solution = solveVirtualTarget(shooter, target, robotVelocity);
if (solution.status() != CONVERGED) {
    inhibitFeeder();
    holdLastValidatedAimOrStopTurret();
}
`}</JavaCode>

The convergence `tolerance` decides when "close enough" is reached. `MAX_ITERATIONS` guarantees only
that computation terminates; it does **not** make the last iterate a valid aim. The monotone table from
idea 2 helps keep the slope condition above true, while the explicit status safely handles invalid or
non-contractive cases.

<Admonition type="warning" title="Hardware reality: ready is a band, not one number">

Do not wait for an encoder reading to equal the target exactly. A match robot should use a readiness band,
because encoder quantization, loop timing, shot disturbance, and battery sag make exact equality a trap.

</Admonition>

## Research extensions: nonlinear coast and full-state turret tracking

### The robot is braking while the shot happens

The virtual-target math above quietly assumes the robot holds a constant velocity through the feeder
delay and the flight. It usually doesn't. A driver who decides to shoot tends to release the sticks,
and the robot coasts down under back-EMF braking and viscous drag. Feed the solver the velocity from
the moment of the trigger pull and it leads the target too far.

The fix starts with a measurement, not a model. Drive the robot up to a speed, cut power, and record
how far it rolls. On real drivetrains the stopping distance fits a quadratic with a linear term:

$$
D(v) = a v^2 + b v
$$

The same fit shows up in path following — Pedro Pathing brakes with it, and the
[Pedro deep-dive](../advanced-topics/how-pedro-pathing-works.mdx) covers that side. Here we need more
than the stopping distance. We need the whole coast: where is the robot, and how fast is it going,
half a second from now?

The fit already contains the answer. A braking-distance curve $D(v)$ implies a deceleration at every
speed — differentiate the relation between distance and speed and you get:

$$
\dot{v} = -\frac{v}{2av + b}
$$

<EquationLegend
  items={[
    {symbol: 'v\u0307', meaning: 'the deceleration implied by the measured braking curve, rather than assumed to be constant', unit: 'in/s\u00b2'},
    {symbol: 'a, b', meaning: 'the same two fitted coefficients from D(v) above: a is the ideal constant-deceleration part, b the viscous drag part'},
  ]}
/>

Separate the variables and the messy right side turns into something integrable:

$$
2a\,(v-v_0) + b\ln\!\left(\frac{v}{v_0}\right) = -t
$$

<EquationLegend
  items={[
    {symbol: 'v_0', meaning: 'the entry speed: how fast the robot was going when the coast began', unit: 'in/s'},
    {symbol: 'ln', meaning: 'the natural logarithm, appearing because separating the variables leaves a 1/v term to integrate'},
    {symbol: 'the minus t', meaning: 'time enters with a negative sign because the robot is slowing. Solving this relation for v given t is what the branches below do'},
  ]}
/>

The logarithm now receives the dimensionless speed ratio $v/v_0$. Before evaluating a special function,
validate that $a$, $b$, and $v_0$ are finite and nonnegative and that the query time $t$ is finite and
nonnegative. Then handle the limiting branches directly:

$$
\begin{array}{ll}
v_0=0: & v(t)=0,\quad x(t)=0,\\[2pt]
a=0,\ b>0: & v(t)=v_0e^{-t/b},\quad x(t)=bv_0\left(1-e^{-t/b}\right),\\[2pt]
b=0,\ a>0: & v(t)=\max\!\left(v_0-\dfrac{t}{2a},0\right),\quad
x(t)=a\left(v_0^2-v(t)^2\right).
\end{array}
$$

If $v_0>0$ and $a=b=0$, the fitted stopping model supplies no valid coast dynamics, so reject it. Reject
negative fitted coefficients rather than sending them into a formula outside its physical domain.

Only the general branch $a>0$, $b>0$, $v_0>0$ needs the **Lambert W function** (the inverse of $u e^u$):

$$
v(t) = \frac{b}{2a}\,W\!\left(\frac{2a v_0}{b}\,
\exp\!\left(\frac{2a v_0 - t}{b}\right)\right)
$$

<EquationLegend
  items={[
    {symbol: 'W(\u00b7)', meaning: 'the LAMBERT W function: the inverse of u\u00b7e\u1d58. It exists because v appears both inside a logarithm and outside it, and no rearrangement separates them'},
    {symbol: 'why it is needed', meaning: 'the previous line mixes v linearly and logarithmically. Lambert W is the standard tool for exactly that shape; look it up before assuming the algebra was botched'},
  ]}
/>

Both $2av_0/b$ and $(2av_0-t)/b$ are dimensionless, so the exponential and Lambert-W arguments are
well-defined. This closed form is a derivation for the research model, not a request to add Lambert W to
the robot runtime.

The distance covered comes for free, with no second integral. The robot's remaining stopping
distance is always $D$ of its current speed, so the ground it has covered is the difference:

$$
x(t) = D(v_0) - D(v(t))
$$

<EquationLegend
  items={[
    {symbol: 'a, b', meaning: 'the fitted braking coefficients; b absorbs back-EMF and viscous drag', unit: 's²/m, s'},
    {symbol: 'v_0', meaning: 'robot speed at the moment power is cut', unit: 'm/s'},
    {symbol: 'W', meaning: 'the Lambert W function, the inverse of u·eᵘ', unit: 'unitless'},
    {symbol: 'v(t), x(t)', meaning: 'closed-form speed and distance covered t seconds into the coast', unit: 'm/s, m'},
  ]}
/>

With $v(t)$ and $x(t)$ in closed form, the deployed controller projects the robot's pose and velocity
about half a second into the future — scalar coast applied along the current velocity direction — and
hands that *projected* state to core idea 3's fixed-point solver. That one projection buys three
things at once:

1. **The deceleration is priced in.** The virtual target is computed from where the robot will be,
   not where it was when the trigger was pulled.
2. **The turret gets its command early.** A servo turret lags its command; aiming at the projected
   state means the turret arrives on time instead of chasing.
3. **The measured initial state carries the battery effect.** Battery voltage changes the speed the
   drivetrain can attain and the behavior of active braking, but it does not multiply a passive coast
   trajectory that starts from a measured $v_0$. Use the measured $v_0$ in the zero-power coast model;
   characterize active braking separately at the voltages where it will run.

:::warning[Fit the coast you actually use]
These coefficients are for a zero-power coast — hands off the sticks. A follower that brakes actively
(Pedro applies about $-0.2$ power) stops much shorter. The $D(v) = av^2 + bv$ form holds for both;
the numbers do not transfer. Fit each behavior separately.
:::

### The turret has to arrive with the right velocity and acceleration

Everything so far computes *where* to aim. But while the robot moves, that answer keeps changing:
the virtual target sweeps across the field, so the turret angle that hits it is a moving reference
$\theta^*(t)$, not a setpoint. Tracking a moving reference is the one job a position-only controller
cannot do cleanly. For the ideal kinematic plant $\dot\theta=u$, a P controller chasing a reference
that ramps at $\omega^* = d\theta^*/dt$ settles into a permanent lag:

$$
e_{ss} = \frac{\omega^*}{k_P}
$$

<EquationLegend
  items={[
    {symbol: 'e_ss', meaning: 'the STEADY-STATE error: the lag that remains forever once transients have died out. Not an error that decays'},
    {symbol: '\u03c9* = d\u03b8*/dt', meaning: 'how fast the target heading itself is moving. A star marks a reference throughout this page'},
    {symbol: 'the whole result', meaning: 'a P controller tracking a ramp always lags by exactly this much. Raising k_P shrinks it but never removes it, which is the argument for the velocity feedforward below'},
  ]}
/>

For a real turret, the coefficient depends on the motor and mechanism dynamics, but the same structural
lag remains: a position-only controller produces the command only after error exists. Raising $k_P$
usually shrinks that lag at the cost of noise sensitivity and reduced stability margin; it does not
provide the missing reference-velocity command.

The clean fix is the full-state reference from
[state-space control](../state-space-control/state-feedback.mdx). The turret is a two-state
mechanism, $\mathbf{x} = [\theta, \omega]$, and the solver should hand it *both* states:

$$
u = K(\mathbf{r} - \mathbf{x})
  + k_S\operatorname{sign}(\omega^*)
  + k_V\omega^*
  + k_A\alpha^*,
\qquad
\mathbf{r} = \begin{bmatrix} \theta^* \\ \omega^* \end{bmatrix}
$$

<EquationLegend
  items={[
    {symbol: '\u03b8*, \u03c9*, \u03b1*', meaning: 'the reference heading, angular velocity and angular acceleration the aim solver produced, all three of them'},
    {symbol: 'r', meaning: 'the reference VECTOR: both states at once, which is what lets K correct position and rate together'},
    {symbol: 'K', meaning: 'the state-feedback gain, a row of two numbers here: one for heading error and one for rate error'},
  ]}
/>

<EquationLegend
  items={[
    {symbol: 'theta*', meaning: 'aim angle from the fixed-point solver, evaluated at the projected pose', unit: 'rad'},
    {symbol: 'omega*', meaning: 'how fast the aim angle is sweeping — the reference velocity', unit: 'rad/s'},
    {symbol: 'alpha*', meaning: 'reference angular acceleration, d omega*/dt', unit: 'rad/s²'},
    {symbol: 'K', meaning: 'state-feedback gain, one entry per state (from LQR or pole placement)', unit: 'V per error'},
    {symbol: 'k_S sign(omega*)', meaning: 'identified static-friction feedforward', unit: 'V'},
    {symbol: 'k_V omega*', meaning: 'identified velocity feedforward', unit: 'V'},
    {symbol: 'k_A alpha*', meaning: 'identified acceleration feedforward', unit: 'V'},
  ]}
/>

The feedforward does the actual tracking work; the feedback only cleans up disturbances. And when
$\mathbf{x} = \mathbf{r}$, the turret is not just pointing at the aim point — it is *moving with
it*, so it stays correct through the whole release window instead of being right for one instant.
That is the physical meaning of a full-state reference, and it is exactly what WPILib's
`loop.setNextR(thetaStar, omegaStar)` exists to accept.

For constant-velocity tracking, $\alpha^*=0$, so the static and velocity terms remain. An accelerating
reference additionally needs $k_A\alpha^*$. Estimate both derivatives with seam-safe angle differences:

<JavaCode league="FTC" label="Turret tracking with velocity and acceleration feedforward">{`AimSolution aim0 = solveVirtualTarget(poseAt(0));
AimSolution aim1 = solveVirtualTarget(poseAt(DT));
AimSolution aim2 = solveVirtualTarget(poseAt(2 * DT));

if (aim0.status() != CONVERGED || aim1.status() != CONVERGED
        || aim2.status() != CONVERGED) {
    inhibitFeeder();                  // never fire an unvalidated solution
    holdLastValidatedAimOrStopTurret();
    return;
}

double theta0 = aimAngle(aim0, poseAt(0));
double theta1 = aimAngle(aim1, poseAt(DT));
double theta2 = aimAngle(aim2, poseAt(2 * DT));

double omegaStar = wrap(theta1 - theta0) / DT;      // radians/second
double omegaNext = wrap(theta2 - theta1) / DT;
double alphaStar = (omegaNext - omegaStar) / DT;    // radians/second^2

double feedforward = kS * Math.signum(omegaStar)
        + kV * omegaStar
        + kA * alphaStar;

double volts = K_POS * (theta0 - measuredTurretAngle)
        + K_VEL * (omegaStar - measuredTurretRate)
        + feedforward;

double vbat = voltageSensor.getVoltage();
if (!Double.isFinite(vbat) || vbat <= MIN_VALID_BATTERY_VOLTS) {
    turret.setPower(0);
    return;
}
turret.setPower(clamp(volts / vbat, -1, +1));
`}</JavaCode>

`poseAt(t)` is the coast-projected robot state $t$ seconds from now. The turret must not merely point
where the target *is*; it must move at the rate the aim point is moving — so the aim is solved three
times at three nearby instants and the answers are differenced.

<Exercise title="Why each difference is wrapped, and why three solutions">

The three angles are absolute bearings, and two of them can straddle the $\pm\pi$ discontinuity.
Construct such a case and compute `omegaStar` with and without the `wrap`. Then work out why the
solver runs *three* times rather than two: two give you a rate, so what does the third buy, and which
term above would be missing without it?

<Solution>

Take `theta0 = 3.10` and `theta1 = -3.10` rad with `DT = 0.02`. The true motion is about 0.08 rad
across the seam, so `omegaStar` should be roughly 4 rad/s. Unwrapped, the difference is $-6.20$ and
the rate comes out at $-310$ rad/s — the turret slams the other way at full authority.

The third solution gives a second rate, and differencing the two rates gives `alphaStar`. Without it
the $k_A\alpha^*$ term has nothing to multiply, so the feedforward is correct only while the aim point
moves at constant angular rate — which it does not do when the robot is turning or the geometry is
changing.

</Solution>

</Exercise>

<Exercise title="Closing the loop on rate, not just position">

`K_VEL` closes the loop on rate rather than position. A turret that only tracks position always lags a
moving target by however long it takes position error to build up. Work out that lag for a target
sweeping at 1 rad/s with a position-only loop.

<Solution>

At steady state a position-only loop settles where `K_POS * error` equals the voltage needed to sustain
1 rad/s — so the error never reaches zero, it reaches whatever standing offset produces that voltage.
With a typical turret that is a tenth of a radian or so of permanent lag, which at competition range is
a miss. The rate term supplies the sustaining voltage directly, so the position error is free to go to
zero.

</Solution>

</Exercise>

`MIN_VALID_BATTERY_VOLTS` is a team-validated sensor-sanity threshold, not a universal FTC cutoff.

This also reframes the turret-lead trick from the coast projection. A servo turret has a position-only interface —
there is nowhere to put $\omega^*$ — so aiming it at the *projected* pose is the poor man's velocity
reference. A motor-driven turret under state feedback consumes $[\theta^*, \omega^*]$ directly and
removes the ideal steady ramp lag without an extra empirical lead. Real sensing and command latency,
model error, saturation, and the finite-difference estimate remain, so projection or measured lead may
still be necessary on hardware.

:::warning[A spinning turret changes the shot]
While tracking, the turret adds a tangential component to the exit velocity — roughly
$\omega^* \cdot r_{\text{exit}}$, the sweep rate times the distance from the turret axis to the
release point. Keep the release radius small by design, or fold the term into the core fixed-point solve as
extra launcher velocity. Measure it before deciding it is negligible.
:::
