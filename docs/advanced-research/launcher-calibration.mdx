# Convert the Model into Robot Commands

<Difficulty level="Medium" />

<Abstract>
The simulator thinks in meters per second and degrees. The robot thinks in encoder ticks and servo
positions. This lesson turns a chosen shot into tables of wheel speed, hood position, and flight time,
and sets up the checks that have to pass before the feeder releases a ball.
</Abstract>

<Admonition type="note" title="Builder outcome and prerequisites">

You'll build three lookup tables, from distance to wheel speed, hood position, and flight time. Each
lookup returns a value and whether it ran off the end of the table. You'll also measure how close the
wheel and hood have to be before firing. The full analysis uses high-speed video and curve fitting, but
on an FTC robot what matters most is clear units, table limits, measurements taken at the same moment,
and testing on shots you didn't tune with.

</Admonition>

You have a trajectory that tolerates errors. Sending its 5.25 m/s exit speed directly to a motor controller still cannot make the shot: the encoder reports wheel motion, and the ball does not leave at the wheel’s surface speed.

<LauncherMechanism />

## Build the static layer first

1. Measure the shooter-to-target geometry and define the distance reference.
2. Collect stationary shots and create wheel, hood, and rim-time knots.
3. Query them with bounded, shape-preserving interpolation that reports clamping.
4. Measure wheel and hood readiness instead of assuming a command has been reached.
5. Log the requested values, measured values, release time, and result for every shot.

Shooting on the move builds on this. It can't fix a stationary table with the wrong units, distances
measured from the wrong spot, or wrong timing.

## Worked example: encoder ticks to ball speed

For a wheel radius of **0.0692 m** and **28 encoder counts per revolution**, an encoder velocity of **1,500 ticks/s** corresponds to:

$$
v_{\rm wheel}=2\pi(0.0692)\frac{1500}{28}\approx23.29\ \mathrm{m/s}.
$$

The ball only picks up about a quarter of that. With the measured average ratio, $\eta=0.259$, the ball leaves at about $0.259\times23.29\approx\mathbf{6.03\ \mathrm{m/s}}$. (That's arithmetic with the average, not a measured shot.)

:::tip[Predict the unit conversion]
Increase the encoder reading from 1,500 to 1,650 ticks/s. Which speeds should increase by 10% if η stays fixed? Change the slider and check the conversion, then reset the example.
:::

<TransferExperiment />

Seven tracked shots in the paper averaged η = **0.259**, with a standard deviation of **0.031** (95% interval for the average: **0.230 to 0.288**). Those shots used different speeds, angles, and distances, so the spread shows how much η varies between settings, not how repeatable one setting is. The camera wasn't calibrated precisely enough to measure drag, just this ratio. Source: paper §9.

## Measure a stronger transfer estimate

For launch $j$, synchronize the wheel encoder and ball measurement at release, then calculate:

$$
\eta_j=\frac{\lVert\mathbf v_{\text{exit},j}\rVert}
{r\,\omega_{\text{wheel},j}}.
$$

You need two measurements at the same moment: the wheel's surface speed **when the ball leaves**, and the ball's speed then. Averaging the wheel speed over a longer stretch throws η off, because the wheel slows down while it pushes the ball.

Several ways to measure better than one uncalibrated video:

| Method | What it measures well | Main limitation |
|---|---|---|
| **Two optical gates near the exit** | Transit time over a surveyed baseline gives a direct local speed without differentiating video pixels. | The wide, perforated ball can interrupt a beam inconsistently; use multiple beams or a light curtain and calibrate the trigger geometry. |
| **High-frame-rate video + backward integration** | A tracked post-release state can be propagated backward through the drag model to the release plane. It also estimates launch angle. | Pixel noise first enters a velocity difference, then grows during backward propagation. Camera geometry, release time, and the force model must be known. |
| **Multi-frame forward fit** | Every tracked center constrains one release speed and angle. Residuals reveal a poor fit instead of hiding it in one derivative. | It needs an optimizer and calibrated timestamps. A short arc usually cannot identify exit speed and drag coefficient independently. |
| **Radar or a validated ball chronograph** | Direct speed measurements make a useful independent reference for the camera pipeline. | Alignment, measurement volume, and a nonstandard perforated projectile must be checked experimentally. |

:::tip[Try the inverse problem]
Use **Clean 480 fps**, then add one pixel of position noise. Move the backtracking frame later in the flight and compare the three-frame estimate with the 18-frame forward fit. Higher frame rate reduces time discretization and motion blur, but a shorter frame interval also makes a two-frame velocity estimate more sensitive to pixel noise.
:::

### Backward with the same integrator

Suppose calibrated video provides three consecutive ball centers around time $t_k$. Estimate velocity with the centered difference

$$
\hat{\mathbf v}_k=\frac{\mathbf p_{k+1}-\mathbf p_{k-1}}
{t_{k+1}-t_{k-1}},
$$

form the state $[x_k,z_k,\hat v_{x,k},\hat v_{z,k}]$, and run RK4 with a **negative** step until the estimated release time. The recovered velocity magnitude divided by synchronized wheel surface speed gives η. Use early post-release frames: reversing a dissipative drag model amplifies state and model errors, so a long backward reconstruction is fragile.

The experiment uses this procedure exactly, with synthetic camera noise and the paper’s flight equations. It then compares a stronger batch estimate:

$$
(\hat v_0,\hat\theta)=\arg\min_{v_0,\theta}
\sum_i \left\lVert
\mathbf p_{\text{model}}(t_i;v_0,\theta)-\mathbf p_{\text{video},i}
\right\rVert^2.
$$

Each candidate release state is integrated **forward** to all observed frames. This avoids constructing one noisy instantaneous velocity and produces a residual in millimetres that can be inspected. A production fit should also account for camera calibration uncertainty and reject frames where the ball is occluded or blurred.

### A practical collection protocol

1. Place a surveyed calibration board in the launch plane, correct lens distortion, use a short exposure, and verify the true frame timestamps instead of trusting only the nominal FPS label.
2. Record the encoder at high rate. Add a visible synchronization LED or electrical trigger so the video and encoder clocks share a release event.
3. Track the ball center for the first clear frames after it loses contact. Keep the raw pixels, confidence score, timestamps, hood setting, ball ID, battery voltage, and wheel-speed trace.
4. Estimate exit speed with optical gates or the multi-frame fit. Use backward integration as a cross-check; disagreement larger than the stated uncertainty is a reason to inspect timing, camera geometry, or the model.
5. Repeat each fixed configuration enough times to measure shot-to-shot spread, then validate the resulting command map on held-out distances and balls.

Don't assume η is one fixed number. Measure how it changes with the things that affect contact, like wheel speed, hood position, squish, and ball wear. Shuffle the order of settings so the battery warming up doesn't look like η changing with speed. These are suggestions for a better experiment; the paper only has the seven-shot estimate above.

## Query three calibrated maps

The deployed pipeline is:

**Estimated distance → flywheel target + hood position + rim flight time → ready bands → release.**

The wheel and hood values started from the simulator and were then adjusted with real shots. The flight
times are the time to reach the rim on the way down. That's more accurate than treating one η as the
whole story.

The simulator's `sweep_targets` and `build_lut` outputs are predictions, a starting point for test
shots. The robot's `Distances`, `velValues`, and `hoodValues` arrays are in robot units: inches, ticks
per second, and servo position. A hood position of 0.3 isn't 0.3 radians, and 5.25 m/s isn't an encoder
setting. Write down where distances are measured from and what the flight time measures, next to each
table.

Return everything from a lookup together: `distance`, `wheelTarget`, `hoodTarget`, `rimTofSeconds`,
`clamped`, and `calibrationRevision`. Then later code can refuse a distance off the table, and the logs
show exactly which table produced each shot.

Between measured distances, the in-between values should follow the shape of the data. A natural cubic
spline can bulge upward between equal values. A monotone cubic Hermite interpolation keeps a flat
stretch flat.

<CalibrationLookup />

The flat stretch comes from the [season's launcher table](https://github.com/stoicescueric/YaoMing/blob/75db349d/TeamCode/src/main/java/org/firstinspires/ftc/teamcode/Hardware/Outtake/Launcher.java): **100, 110, and 120 inches all ask for 1,700 ticks/s**. Compare the curves near 105 inches. A bump there would be something the interpolation made up, not something anyone measured. The demo uses the whole table and shows the 80 to 130 inch part.

<details>
<summary>How monotone Hermite avoids the bulge</summary>

First compute the secant slope between adjacent knots. Flat intervals get zero tangents at both ends; tangents opposing the secant are also zeroed. For a nonzero secant $s$, normalize the two endpoint tangents as $\alpha=m_0/s$ and $\beta=m_1/s$. The Fritsch–Carlson construction projects them into the sufficient monotonicity region $\alpha^2+\beta^2\le9$.

That keeps each stretch between two measurements from overshooting. It doesn't make the measurements
themselves right. Source: paper §5.7 and its Fritsch–Carlson reference.

**A bug to know about:** the season's Java computes $h=\sqrt{\alpha^2+\beta^2}$ but only limits the slopes
when $h>9$, when it should when $h>3$. The lesson's version uses 3. Equal values still get flat slopes
in the Java, so the flat stretch above is fine, but other tables might overshoot. Check every stretch
when you change the table.

</details>

## What the season motor controller actually does

The [season velocityController.java](https://github.com/stoicescueric/YaoMing/blob/75db349d23551665a93aaa0b5266ba4a10316ac6/TeamCode/src/main/java/org/firstinspires/ftc/teamcode/Util/Controllers/velocityController.java)
computes feedforward, scales that term by nominal/measured battery voltage, and adds PID feedback.
With bang-bang enabled, a large error then **replaces** the combined command:

| Condition | Command before the final clamp |
|---|---|
| More than 110 ticks/s below target | +1.0 motor power |
| More than 50 ticks/s above target | −0.2 motor power |
| Between those thresholds | PID + voltage-compensated feedforward |

The defaults are $k_P=0.004$, $k_I=k_D=0$, $k_V=0.000336$, and $k_S=0.05$, all in motor power rather
than volts. The −0.2 power actively brakes the wheel, which slows it faster than just coasting at zero.

The season's `isReady()` only checks the wheel speed. The wheel-and-hood check below is how it should
work, but note that a commanded servo position doesn't tell you the hood actually got there.

## The newer robot is a different deployment

At [8374312f](https://github.com/stoicescueric/YaoMing/blob/8374312fa7ba75b87197c2dbaeee5c46624722fa/TeamCode/src/main/java/org/firstinspires/ftc/teamcode/Hardware/Outtake/Launcher.java),
the launcher defaults to **useRST = true**. Its dispatch selects RST before the alternate
Team254 and legacy controllers. The newer distance table requests 1,950 ticks/s at both 110 and
127 inches, rather than the season's 1,700-tick shelf.

The [RST implementation](https://github.com/stoicescueric/YaoMing/blob/8374312fa7ba75b87197c2dbaeee5c46624722fa/TeamCode/src/main/java/org/firstinspires/ftc/teamcode/Util/Controllers/RSTFlywheelController.java)
is built from measured feedforward constants, as in [RST pole placement](../advanced-topics/rst-pole-placement.mdx).
With a new controller and new tables, the paper's season results don't apply until it's tested again.

## Java: request release only inside the ready bands

<JavaCode league="FTC" label="Check the calibrated launcher state">{`boolean launcherReady(double wheelTarget, double wheelMeasured,
                      double hoodTarget, double hoodMeasured) {
    if (!Double.isFinite(wheelMeasured)
            || !Double.isFinite(hoodMeasured)) return false;
    return Math.abs(wheelTarget - wheelMeasured) <= wheelReadyBand
            && Math.abs(hoodTarget - hoodMeasured) <= hoodReadyBand;
}`}</JavaCode>

Measure the bands on the mechanism, in the same units as the signals. Waiting for one exact encoder value would never happen. This is one part of the decision to fire; the table lookup has to be valid too, and the feeder delay comes after.

### The combined release gate

Before starting the feeder, require a lookup that's on the table, a recent pose and velocity if the
robot is moving, an aim calculation that settled, the wheel, hood, and turret all ready, and the robot in
a state where firing is allowed. Log which check stopped each shot, so "the shooter wasn't ready" turns
into something you can actually fix.
