# Build a Robust Moving Shooter

<Abstract>
This elective turns a research system into an FTC implementation path. You will see what runs offline,
what runs every robot loop, what must be measured on your own launcher, and what evidence tells you the
system is ready to fire. The goal is to understand the algorithms well enough to build and challenge your
own version, not to copy one season's constants.

## The whole shooter in one pass

The robot launches a light, perforated ball through a raised opening. A useful shot must survive more
than one ideal calculation: the ball varies, the launcher transfers wheel speed imperfectly, the chassis
moves, and the goal can reject a ball that entered geometrically.

<Workflow />

The first three steps produce a recommendation **offline**. The robot does not run thousands of
trajectories during a control loop. It queries calibrated tables, solves a small moving-target update,
controls the mechanism, checks readiness, and releases.

## Adopt the system in layers

You do not need the complete research pipeline before the first useful implementation.

| Level | Build | What it gives the team |
|---|---|---|
| Reliable static shooter | measured wheel and hood tables, flight-time table, interpolation, readiness gate | repeatable stationary releases and the data required by later stages |
| Shoot while moving | field-frame velocity, virtual-target iteration, convergence and range status | aim correction for inherited chassis motion |
| Model-guided selection | drag-aware flight solver, geometric entry test, bounded make-window search | fewer physical candidates and an explanation of why one command is less fragile than another |

Start with the static layer if your team needs a competition result quickly. Add motion compensation
only after pose, velocity, release delay, and flight time are trustworthy. Add the offline model when you
want to reduce calibration search or study sensitivity.

## Five lessons, five build artifacts

1. **[Build the Offline Flight Model](./trajectory-simulation.mdx).** Produce a function that maps exit
   speed, angle, and geometry to a descending rim crossing, entry velocity, and time of flight.
2. **[Choose a Shot with Error Margin](./robust-shot-selection.mdx).** Produce an offline selector that
   compares nearby speed-angle commands and exports the most tolerant eligible command.
3. **[Convert the Model into Robot Commands](./launcher-calibration.mdx).** Produce bounded wheel, hood,
   and flight-time tables plus a measured release-readiness gate.
4. **[Compensate for Robot Motion](./shoot-on-the-move.mdx).** Produce a virtual target and status object
   from shooter pose, target pose, chassis velocity, release delay, and flight time.
5. **[Test, Diagnose, and Hand Off](./model-vs-empirical-lut.mdx).** Produce a staged test record that
   separates geometric misses, bounce-outs, mechanism recovery, and motion-compensation failures.

The first two lessons share the paper's **70-inch (1.778 m) front-lip distance** and selected
**5.25 m/s, 58°** worked command. Every experiment has a reset action that returns to its worked example.

## Know what belongs offline and on the robot

| Stage | Input → output | Execution boundary |
|---|---|---|
| Flight model | exit speed and angle → descending rim event and flight time | offline simulator |
| Robust selection | event map and target distance → tolerant nominal release state | offline simulator |
| Calibration | release state and physical trials → wheel, hood, and TOF table knots | pit and practice field |
| Motion compensation | pose, velocity, and TOF → virtual target and solver status | every robot loop |
| Actuation | table targets → flywheel, hood, turret, and feeder commands | every robot loop |
| Validation | physical launches → entered, bounced out, or missed | logged test and match data |

A CSV of ideal ball speed and angle is not a motor table. The calibrated launcher maps absorb wheel
slip, compression, surface condition, motor response, and mechanism geometry that the flight model does
not know.

## Prerequisites for full understanding

The builder route assumes basic Java, vectors and coordinate frames, consistent units, interpolation,
and timestamped sensor logging. The complete derivations additionally use ordinary differential
equations, RK4 integration, cubic Hermite interpolation, bounded optimization, and fixed-point
iteration. Those topics are prerequisites for reproducing the mathematics; the lessons still expose
the inputs, outputs, invariants, and tests needed to implement each stage with a trusted library.

Before motion compensation, complete [measured loop timing](../software-architecture/discretization.mdx),
[feedforward](../control-theory/feedforward.mdx), and the
[pose-estimation contract](../path-following/pose-estimation-contract.mdx).

## Remeasure these values on every launcher

| Quantity | Why it cannot be copied |
|---|---|
| release position and target geometry | mounting and field references change the flight problem |
| usable speed-angle envelope | wheel, hood, ball, and motor limits differ |
| distance-to-wheel and distance-to-hood knots | actuator commands are robot-specific |
| distance-to-flight-time knots | motion compensation depends on the actual release-to-entry event |
| wheel and hood ready bands | recovery, sensing, and acceptable shot error differ |
| release delay | feeder timing changes the inherited displacement |
| velocity frame and sign | one frame or sign mistake leads the target in the wrong direction |
| inheritance gain | projectile-platform coupling must be identified and validated |

## Freeze the source before comparing results

The simulator snapshot used by the paper is
[09663d68](https://github.com/stoicescueric/Trajectory-Simulation/tree/09663d6868fd0cc781dc28448cc3f6ace828da1a).
Its `backend/physics.py` and `backend/verify.py` match the SHA-256 hashes printed in the final paper. The
paper's older `decode_sim/decode_sim` directory reference now corresponds to `backend/`.

The reported season results belong to robot revision **75db349d**, frozen by paper section 6. The newer
[8374312f robot snapshot](https://github.com/stoicescueric/YaoMing/tree/8374312fa7ba75b87197c2dbaeee5c46624722fa)
has different tables, radial and lateral motion weights, and an RST controller enabled by default. The
lessons explain those changes without assigning the season's measured outcomes to untested newer settings.

:::note[Keep three results separate]
**Numerical verification** asks whether code solves the stated equations. **Target entry** asks whether
the physical ball reaches the opening. **Retained score** asks whether it stays scored after contact. A
bounce-out is an entry, and the flight model does not simulate the contact that caused it.
:::
