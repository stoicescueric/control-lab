# Module 5 · State-Space Control

<Abstract>
State space is a way to make one model do four jobs: predict the mechanism, expose every state that
matters, estimate what sensors cannot measure directly, and choose feedback gains from stated design
goals. This module follows the same model–observer–controller structure used by WPILib, then reduces it
to the arithmetic an FTC robot actually needs.
</Abstract>

## Start with the decision, not the matrices

State-space control is worth learning whenever a mechanism has coupled states, an important hidden
state, or a model you want to test before the robot is assembled. It is often unnecessary for a
single flywheel or elevator that already behaves well with feedforward plus PID.

Use this gate before committing to the module:

| Your mechanism | Start with | Move to state space when… |
|---|---|---|
| One measured velocity | feedforward + P/PID | model-based gain selection or filtering saves real tuning time |
| Position and velocity | feedforward + PD/PID | the two gains need to be designed together |
| Coupled axes or several states | state feedback | independent loops interact or fight |
| A state is hidden or noisy | observer + feedback | raw differentiation or filtering adds too much lag |
| Model changes often | model-based workflow | you can re-identify and recompute faster than retuning |

:::note[What this module promises]
You will finish with a model you can step by hand, a plotted observer trace, an LQR design that respects
voltage saturation, and an FTC deployment decision backed by measured loop timing. The goal is a
working engineering chain, not familiarity with matrix vocabulary.
:::

## Four checkpoints

1. **[Model and inspect the state](./state-feedback.mdx).** Choose $x$, $u$, and $y$; turn measured
   $k_V$ and $k_A$ into $A$ and $B$; discretize for the real loop; inspect position and velocity as one
   point in a phase plane.
2. **[Estimate what the sensor hides](./observers.mdx).** Run predict and correct, expose model mismatch
   and sensor noise, and understand why a controller must use the estimate rather than a raw derivative.
3. **[Choose feedback with LQR](./lqr.mdx).** Convert error and voltage tolerances into a sampled gain,
   then inspect response, effort, saturation, and timing assumptions.
4. **[Decide whether it is worth it in FTC](./ftc-decision.mdx).** Compare the Control Hub and roboRIO
   execution environments, count the runtime arithmetic, and use a deployment checklist rather than a
   fashionable-controller rule.

This ordering follows WPILib’s official state-space material: introduction, end-to-end controller,
observers, then debugging. Control Lab adds the missing FTC translation and keeps every important
graph driven by reader-controlled inputs.

## Prerequisites that save time

- You can name the state, input, output, and units from the
  [state-space preface](../preface/why-math-matters/state-space.mdx).
- You have validated $k_V$ and $k_A$ on held-out data using
  [system identification](../control-theory/system-identification.mdx).
- Your loop measures time, handles pauses, and applies voltage consistently as described in
  [From Math to a Loop](../software-architecture/discretization.mdx).
- You know the scalar predict/correct idea from the [Kalman lesson](../signal-processing/kalman.mdx).
