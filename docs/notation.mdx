# Conventions & Notation

<Abstract>
Every lesson uses the same coordinate frames, angle conventions, units, and symbol names, and this page
lists them. If a sign or symbol in a formula looks wrong, check here before assuming it's a typo.
</Abstract>

## Coordinate frames

All 2-D geometry in the curriculum uses one right-handed convention:

| Convention | Meaning |
|---|---|
| $+x$ | **forward** (robot frame) / toward the far wall (field frame) |
| $+y$ | **left** |
| $+\theta$, $+\omega$ | **counter-clockwise**, viewed from above |
| angles | radians internally; wrapped to $[-\pi, \pi)$ before use in any controller |

Two frames appear constantly:

- **Field frame**: fixed to the field. Poses $(x, y, \theta)$ and paths live here.
- **Robot frame**: rides on the robot: $+x$ out the front, $+y$ out the left side. Drive commands
  $(v_x, v_y, \omega)$ live here, because that is what the [mecanum mixer](./path-following/mecanum-kinematics.mdx) consumes.

Converting a field-frame vector into the robot frame is a rotation by $-\theta$:

$$
\begin{bmatrix} v_x^{robot} \\ v_y^{robot} \end{bmatrix}
=
\begin{bmatrix} \cos\theta & \sin\theta \\ -\sin\theta & \cos\theta \end{bmatrix}
\begin{bmatrix} v_x^{field} \\ v_y^{field} \end{bmatrix}
$$

:::warning[Sign bugs are convention bugs]
If a wheel fights the others or the robot strafes when told to turn, fix the **convention** (motor
direction, encoder sign, where zero is), not the math. Most mecanum bugs turn out to be one reversed
motor. See [angle wrapping](./path-following/angle-wrapping.mdx) for the $\pm\pi$ seam.
:::

## Units

Derivations use SI unless a section explicitly labels another unit. The equations remain dimensionally
valid in any consistent unit system; FTC snippets may use inches when variable names or comments state
that choice. Convert once at a hardware or library boundary and never mix unit systems in one calculation:

- **Encoder ticks → real units** happens in exactly one constant
  (`METERS_PER_TICK`) — see [From Math to a Loop](./software-architecture/discretization.mdx).
- **Loop time** $\Delta t$ is always the *measured* elapsed seconds, never an assumed constant.
- **Motor commands** are computed in volts, then divided by the measured battery voltage —
  see [voltage compensation](./control-theory/voltage-compensation.mdx).

## Recurring symbols

### Indices, increments, and decorations

These show up in almost every equation on the site.

| Symbol | Meaning |
|---|---|
| subscript $k$ | **the control loop index.** $x_k$ is the value this loop, $x_{k+1}$ the value next loop. It counts loops, not seconds |
| subscript $i$ | an index into a *list*: path points, samples, wheels. Position in a collection, never time |
| $\Delta t$ | the *measured* seconds between loop $k$ and loop $k+1$ |
| $\Delta s, \Delta\theta$ | how far the robot moved and turned during one loop |
| $\dot{x}, \ddot{x}$ | first and second derivative with respect to time: $\dot{x}$ is a velocity, $\ddot{x}$ an acceleration |
| $\hat{x}$ | an *estimate* of $x$, not a measurement of it |
| $\mathbf{x}$ (bold) | a vector or matrix; the same letter unbolded is a single number |
| $A^{\top}$ | transpose: rows and columns swapped |
| $\lVert v \rVert$ | the length of vector $v$ |

So a line like $\mathbf{x}_{k+1} = f(\mathbf{x}_k, \Delta s, \Delta\theta)$ reads: the state vector at
the next loop is some function of the state now, plus how far the robot moved and turned in between.

### Pose & geometry

| Symbol | Meaning | Unit |
|---|---|---|
| $x, y, \theta$ | field-frame pose: position + heading | m, m, rad |
| $v, \omega$ | linear speed, angular velocity | m/s, rad/s |
| $\kappa = 1/R$ | path curvature (radius $R$) | 1/m |

### Control

| Symbol | Meaning |
|---|---|
| $r$ (or setpoint) | the target value |
| $y$ (or measurement) | what the sensor reports |
| $e = r - y$ | error — heading errors always wrapped to $[-\pi, \pi)$ |
| $u$ | the actuator command the controller outputs |
| $k_P, k_I, k_D$ | PID gains (present, past, trend of the error) |
| $k_S, k_V, k_A$ | feedforward: static friction, velocity, acceleration |
| $k_G$ | gravity hold (constant for slides, $k_G\cos\theta$ for arms) |
| $v_{max}, a_{max}$ | the mechanism's real speed and acceleration limits |

The same two feedforward terms go by other names in some lessons, following the code they come from:

| Name | Where it's used | Same as |
|---|---|---|
| $k_F$ | the F in the [PDFL controller](./control-theory/pid.mdx) | $k_G$, the gravity hold |
| $k_L$ | the L in the PDFL controller | $k_S$, the static-friction push |
| `kStatic` | [path followers](./path-following/common-implementation.mdx) | $k_S$, applied only near the target |

### Motors

| Symbol | Meaning | Unit |
|---|---|---|
| $V, I, R$ | applied voltage, winding current, winding resistance | V, A, Ω |
| $k_t$ | torque constant: $\tau = k_t I$ | N·m/A |
| $k_e$ | back-EMF constant: $V_{emf} = k_e \omega$ | V·s/rad |
| $\tau$ | torque (context makes clear when $\tau$ is a *time constant* instead) | N·m |
| $J$ | rotational inertia | kg·m² |

### Estimation

| Symbol | Meaning |
|---|---|
| $\hat{x}$ | the estimate of the state (the hat always means "estimate") |
| $z$ | a sensor measurement |
| $P$ | covariance of the estimate (its uncertainty) |
| $Q, R$ | process-noise and measurement-noise covariance — the two tuning knobs |
| $K$ | Kalman gain: how much of the innovation to believe |
| $H$ | measurement matrix/Jacobian: state space → sensor space |
| $\alpha$ (low-pass) | weight on the **new reading**, $\alpha = 1-e^{-\Delta t/\tau}$ |
| $\alpha$ (complementary) | weight on the **prediction**, $\alpha = e^{-\Delta t/\tau}$, the opposite of the row above |
| $\tau$ | a filter time constant |
| $A, B$ | in the matrix Kalman filter: how the state moves on its own ($A$) and how a command changes it ($B$) |

## Naming in the algorithms

Every algorithm is shown in Java, usually just the method the lesson is about. The rest of the program,
like helper methods, tuned constants, and hardware setup, is left for you to write, so most blocks
won't run if you paste them in on their own. Some blocks do call the FTC SDK directly (`setPower`,
`getVoltage`) where that call is the point of the lesson.

The code is written for Java 8, which is what the FTC SDK compiles by default. Names follow ordinary
Java: `lowerCamelCase` for variables and methods, `SCREAMING_CASE` for tuned constants. Comments only
give units and ranges. Anything worth working out by hand comes after the block as an **Exercise**,
often with a hidden solution.

The names match the math: `kP`, `kV`, `kG` for gains, `dt` for measured loop time, `wrap(angle)` for
wrapping to $[-\pi,\pi)$, and `Pose2d`, `Vector2d`, `PoseSample`, and `moveStatus(...)` from
[Common Implementation](./path-following/common-implementation.mdx), spelled the same everywhere.
