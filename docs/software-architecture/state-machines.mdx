# State Machines

<Difficulty level="Easy" />

<Abstract>
A finite state machine models a subsystem as one current mode plus a small set of legal transitions.
For FTC robots, that makes sequencing code easier to debug because impossible combinations, like intaking and scoring at the same time, become impossible to represent.
</Abstract>

FTC code fails in boring ways before it fails in mathematically interesting ways. A good PID controller
does not save an arm routine that is half blocked by `sleep()`, half controlled by stale booleans, and
impossible to reason about from telemetry.

A state machine is the first architecture tool that gives robot behavior a shape.

## FTC example: the boolean-flag scorer

A scoring subsystem often starts clean:

<JavaCode league="FTC" label="The innocent beginning">{`boolean isIntaking = false;
boolean hasSample = false;
boolean isLifting = false;
boolean isScoring = false;`}</JavaCode>

Then the robot gets more capable. The driver wants cancel. The intake has a beam-break sensor. The arm
needs time to move. The claw needs to release after the arm reaches the top. Suddenly the robot has
many flags, and the flags can disagree.

What does this mean?

<JavaCode league="FTC" label="Contradictory subsystem state">{`isIntaking = true;
hasSample = true;
isLifting = true;
isScoring = false;`}</JavaCode>

Maybe it means the robot is still pulling in a game element while the lift is already moving. Maybe it
means the flags were not reset after the last cycle. Maybe it means the next `if` block will do
something dangerous. The code can enter states the robot should never physically enter.

The bug is not just "too many booleans." The bug is that the subsystem does not have one authoritative
answer to the question: **what mode am I in right now?**

## Visual intuition

Try the machine below. Some driver requests work only from certain states. Illegal requests are not
errors; they are ignored because the transition is not defined.

That is the practical win. A state machine does not merely organize code. It narrows the set of things
the robot is allowed to be.

## Theoretical rigor

A finite state machine has three pieces:

| Symbol | Meaning | FTC scorer example |
|---|---|---|
| $S$ | set of states | `IDLE`, `INTAKING`, `LOADED`, `RAISING`, `SCORING` |
| $E$ | set of events | driver button, sample detected, arm at target |
| $\delta$ | transition function | rule that maps state plus event to next state |

The transition function is:

$$
\delta : S \times E \rightharpoonup S
$$

<EquationLegend
  title="Reading the transition function"
  items={[
    {symbol: 'S', meaning: 'the SET of all states the machine can be in: your enum, written mathematically'},
    {symbol: 'E', meaning: 'the set of all EVENTS that can happen: a button press, a path finishing, a timer expiring'},
    {symbol: '\u03b4 (delta)', meaning: 'the transition function itself: given a state and an event, which state comes next. Not \u0394 for a change in a quantity'},
    {symbol: 'S \u00d7 E', meaning: 'every possible pairing of a state with an event'},
    {symbol: 'the half arrow \u21c0', meaning: 'PARTIAL: not every state and event pairing is defined. Most events do nothing in most states, and that is the point rather than an oversight'},
  ]}
/>

Here, $S \times E$ means "a state paired with an event." The half-arrow $\rightharpoonup$ means the
function is partial: not every event is legal from every state.

A small scorer can be written as a transition table:

| Current state | Event | Next state |
|---|---|---|
| `IDLE` | driver starts intake | `INTAKING` |
| `INTAKING` | sample detected | `LOADED` |
| `INTAKING` | driver cancels | `IDLE` |
| `LOADED` | driver requests score | `RAISING` |
| `RAISING` | arm reaches target | `SCORING` |
| `SCORING` | release timer expires | `IDLE` |

Everything not listed is ignored. That is not laziness; it is the safety property. The machine cannot
be `INTAKING` and `RAISING` simultaneously because `state` has exactly one value.

State machines also make outputs easier to audit. In a simple Moore-style machine, hardware behavior
comes from the current state:

$$
u_k = g(s_k)
$$

<EquationLegend
  items={[
    {symbol: 's_k', meaning: 'which state the machine is in at loop k'},
    {symbol: 'u_k', meaning: 'the actuator command chosen for that loop'},
    {symbol: 'g(\u00b7)', meaning: 'the output function. That it depends on the state ALONE, not on the event that got you there, is what makes this a Moore machine and what makes the behaviour auditable'},
  ]}
/>

Here, $s_k$ is the current state at loop $k$, and $u_k$ is the actuator command chosen for that state.
For example, `INTAKING` runs the intake, `RAISING` commands the arm target, and `IDLE` stops or holds
everything safely.

## Core checkpoint: one enum, one transition gate

This is the minimum useful pattern. `update()` performs one quick slice of work; `enter()` is the only
place that changes state and resets state-local time.

<Pseudocode label="A scorer: one state field, one transition gate">{`SCORER

  states:  IDLE, RAISING, RELEASING
  own:     state          <- IDLE
           time_in_state                  # reset ONLY on entry

  enter(next):                            # the one place state changes
      state         <- next
      time_in_state <- 0

  request_score():                        # an outside event
      if state is IDLE: enter(RAISING)

  update():                               # one slice of work. never blocks.
      if state is IDLE:
          hold the lift
          close the claw

      if state is RAISING:
          command the lift to SCORE_HEIGHT
          if the lift reports it is at target: enter(RELEASING)

      if state is RELEASING:
          open the claw
          if time_in_state >= RELEASE_TIME: enter(IDLE)

  # Work out: why must time_in_state reset inside enter(), and not at the
  #           top of update()? Trace both versions through three loops.
  # Look up:  a non-blocking timer for your SDK. It has to be readable
  #           without waiting on it, which rules out sleep().
`}</Pseudocode>

If you can trace the three legal transitions and confirm that no loop blocks, the core lesson is done.

### Engineering implementation

The deployable FTC pattern is an `enum`, a `switch`, and a timer, but a real autonomous machine
needs more than a pretty transition table. It needs **entry actions**, **timed exits**,
**path-completion guards**, **interference recovery**, and **subsystem updates** that still run every
loop.

What follows is an adapted, teaching-oriented reconstruction of the WolfPackMachina `Auto.java`
pattern — **not** the full file. The original uses `Paths.Path` objects directly as states; this
version wraps the same idea in a smaller, named state set so the architecture is easier to read.

It is all one machine, `AdaptiveAuto`. What follows is its shape, not its source: a state table, the
loop and the gate that owns every transition, and the three handler shapes that keep recurring. Write
the handlers yourself; there are nine of them and they are all variations on those three.

#### The state table: one field holds the mode

A single `current_state` field is the one authoritative answer to "what is the robot doing right
now?" Everything else is bookkeeping the handlers lean on.

<Pseudocode label="AdaptiveAuto - the state table">{`ADAPTIVE AUTO

  states:
      WAIT_FOR_PICKUP      hold the scoring pose until settled
      DISLODGE_CONE        recovery: push a stuck cone free
      ALIGN_LEFT_RAM       contract, then line up on the stack
      LEFT_RAM             follow the pickup path
      CONTESTED_LEFT_RAM   recovery: we were pushed off-line
      ALIGN_CONTESTED      line up to score
      ALIGN_PARK           choose a park square, retract
      PARK_CLOSE           drive into the square
      CYCLE_TRANSFER       hand off intake -> depositor

  the one authoritative field:
      current_state <- WAIT_FOR_PICKUP

  bookkeeping the handlers read:
      scoring_state             which scoring approach we committed to
      time_in_state             reset by the gate, never by a handler
      time_since_settled
      path_complete             this state's path has finished
      parking, contracting      one-shot entry guards
      robot_settled
      slides_position_at_entry  snapshot taken on entry

  # Notice what is absent: no step counter, no sleep, no "phase 2b" boolean.
  # One field answers the question. Everything else is derived from it.
`}</Pseudocode>

#### The loop and the gate

The loop never blocks. It runs the current state's handler and then, whatever state it is in, updates
every subsystem and logs the mode. One gate owns every mode change, so timing and flags always reset
together.

<Pseudocode label="AdaptiveAuto - the loop and the transition gate">{`loop():                        # exactly one pass through. never blocks.
    run the handler for current_state

    # then, regardless of which state we were in:
    tick every subsystem
    log current_state, scoring_state, time_in_state, path_complete

transition_to(next):           # THE ONLY place current_state is written
    if next is current_state and next is not CYCLE_TRANSFER:
        return                 # re-entering a state is a no-op, except
                               # CYCLE_TRANSFER, which is meant to repeat

    current_state    <- next
    time_in_state    <- 0
    time_since_settled <- 0
    clear path_complete, parking, robot_settled
    set contracting

request_park():                # an outside event, through the same gate
    if current_state is not ALIGN_PARK:
        transition_to(ALIGN_PARK)

# Work out: why do the flags reset here instead of in each handler?
#           Add a tenth state on paper and count what you had to remember.
`}</Pseudocode>

#### Three handler shapes

Every one of the nine handlers is one of these three. Once you can write these, the rest of the
machine is repetition.

<Pseudocode label="AdaptiveAuto - entry actions, preconditions, recovery">{`# SHAPE 1 - an entry action, then a non-blocking wait.
align_park():
    if not parking:                  # true on the first loop in this state
        choose the closest park square
        retract the slides
        parking <- true              # ...and only the first loop
    hold still

    if time_in_state > PARK_SETTLE_TIME:   # poll a clock; never sleep on it
        transition_to(PARK_CLOSE)


# SHAPE 2 - a precondition. Refuse to act until the robot is safe.
align_left_ram():
    if contracting and the lift is still above its safe height:
        hold position
        return                       # do nothing this loop. try again next.
    contracting <- false
    contract the robot

    still_following <- follow the alignment path
    if not still_following:
        transition_to(LEFT_RAM)


# SHAPE 3 - a branch. This is what makes it a policy, not a script.
run_left_ram():
    once past 5% of the path: start extending the slides
    still_following <- follow the pickup path
    if still_following: return

    retract the slides
    if the robot was pushed off-line:
        transition_to(CONTESTED_LEFT_RAM)   # recover, then come back
    else:
        transition_to(ALIGN_CONTESTED)      # carry on as planned
    reset the path


# ...and beneath all of it, every loop, in every state:
tick every subsystem():
    tick the drive
    tick the intake      AND run the intake's own state machine
    tick the depositor   AND run the depositor's own state machine

# Look up: "hierarchical state machine". Subsystems running their own
#          machines underneath a top-level one is the standard structure,
#          and it is why update() has to run in every state.
`}</Pseudocode>

This is what makes the example valuable. The state machine is not just replacing `sleep()` with
`if`; it is creating a recoverable autonomous policy. `ALIGN_LEFT_RAM` can refuse to move until the
robot is contracted. `LEFT_RAM` can branch into `CONTESTED_LEFT_RAM` if the robot is pushed off-line.
`ALIGN_PARK` has first-entry logic so the parking target is chosen once, not recalculated every loop.
Every transition resets local timing through the one gate, so `time_in_state` always means "time
since this state began" and never anything else.

In mathematical language, this is still the same partial transition function:

$$
\delta(s_k, e_k) = s_{k+1}
$$

but now the event $e_k$ is not only a button press. It can be "path finished," "650 ms elapsed,"
"robot was interfered with," "slides are below a safe threshold," or "parking has been requested."
That is why autonomous FSMs are so powerful: they turn a linear script into a policy that can react
to the field.

## Hardware reality

<Admonition type="warning" title="Never block the OpMode loop">

`sleep()` and long `while` waits freeze the entire robot. Driver control, sensor updates, telemetry,
and other subsystems all stop. A state machine replaces "wait here" with "check whether the condition
is true this loop."

</Admonition>

<Admonition type="tip" title="Telemetry should name the state">

Print the current state and time-in-state every loop. During a match-debug session, "stuck in
RAISING for 2.4 seconds" is vastly more useful than staring at four unrelated booleans.

</Admonition>

<Admonition type="tip" title="Use state machines inside subsystems">

State machines are excellent for one mechanism with a few clear modes: intake, shooter, lift, claw,
endgame latch. When the problem becomes composing many subsystems into a full autonomous routine, use
[Command-Based Programming](./command-based.mdx) on top of those subsystem internals.

</Admonition>
