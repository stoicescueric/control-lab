# Common Implementation

<Difficulty level="Easy" />

<Abstract>
Every follower in this module — <a href="./pid-to-point">PID-to-point</a>,
<a href="./pure-pursuit">pure pursuit</a>, the <a href="./guided-vector-fields">guided vector field</a> —
leans on the same handful of primitives: a pose and a vector type, angle wrapping, a single "are we there
yet?" completion outcome, the kStatic friction nudge, and one drivetrain entry point. They are collected
here, defined <em>once</em>, so each lesson can show only the logic that is actually new and link back here
for the plumbing. Treat this as the module's small standard library.
</Abstract>

First verify and adapt your library with the [Pose Estimation Contract](./pose-estimation-contract.mdx).
The algorithms throughout Modules 4–5 then call things like `robot.vec()`, `wrap(error)`, `moveStatus(...)`,
and `drive(vx, vy, omega)` without re-deriving them every time. This page is where those names are defined.
Production libraries (Road Runner, FTCLib) ship their own equivalents; these are the minimal versions the
lessons assume.

These names are a contract, not source you can paste. The signatures below are the part that matters —
write the bodies yourself, but keep the names exactly as spelled here, because every later lesson refers
to them by name.

## Geometry: `Vector2d`, `Pose2d`, and `PoseSample`

A 2-D vector supplies the operations followers use (dot, cross, norm, rotate). A `Pose2d` is only
position plus heading, so constructing a target cannot accidentally supply fake measured velocity. The
pose-source adapter returns one atomic `PoseSample` containing the measured pose, its field-frame
velocity, and the timestamp. Field coordinates are $+x$ toward the far wall, $+y$ left, and heading is
CCW positive.

<JavaCode label="Vector2d">{`// A 2-D vector, in field or robot coordinates. The signatures are the
// contract; the algebra behind them is not what needs teaching.
record Vector2d(double x, double y) {
    Vector2d plus(Vector2d b)  { ... }
    Vector2d minus(Vector2d b) { ... }
    Vector2d times(double s)   { ... }

    double dot(Vector2d b)     { ... }   // zero when perpendicular
    double cross(Vector2d b)   { ... }   // signed; the z of the 3-D cross

    double norm()              { ... }
    Vector2d unit()            { ... }   // unchanged if norm is ~ 0

    // (x cos t - y sin t, x sin t + y cos t) -- CCW positive
    Vector2d rotate(double t)  { ... }
}
`}</JavaCode>

Those last two lines are exactly the rows of a rotation matrix.

<JavaCode label="Pose2d and PoseSample">{`// Position AND heading. Deliberately no velocity field.
record Pose2d(double x, double y, double heading) {
    Vector2d vec() { return new Vector2d(x, y); }
}

// One atomic reading from the pose source.
record PoseSample(
    Pose2d pose,               // where we are
    Vector2d fieldVelocity,    // field frame, inches/second
    double timestampSeconds    // when this reading was taken
) {}
`}</JavaCode>

All three `PoseSample` fields come from the same reading. Never assemble one from a pose read this loop
and a velocity read two loops ago. And `Pose2d` deliberately has no velocity field: with one, a *target*
pose could carry a fake measured velocity, and someone would eventually read it. Leaving it out makes
that bug unwriteable.

<Exercise title="Verify rotate by eye">

Check `rotate` on a case your eye can settle: rotating $(1, 0)$ by 90° must give $(0, 1)$.

<Solution>

At $t = \pi/2$, $\cos t = 0$ and $\sin t = 1$, so the first row gives $1(0) - 0(1) = 0$ and the second
gives $1(1) + 0(0) = 1$ — the vector $(0,1)$, pointing $+y$, which is left, which is counter-clockwise.
If you get $(0,-1)$ a sine sign is flipped, and every heading in every follower will be mirrored.

</Solution>

</Exercise>

## Angle wrapping

Heading errors must be wrapped to $[-\pi, \pi)$ so the robot always turns the short way. This is the whole
point of the [angle-wrapping lesson](./angle-wrapping.mdx); the standard one-liner:

<JavaCode label="wrap(angle) -> [-pi, pi)">{`// The angle in [-pi, pi) pointing the same direction as a.
static double wrap(double a) {
    double turn = 2 * Math.PI;
    return ((a + Math.PI) % turn + turn) % turn - Math.PI;
}
`}</JavaCode>

<Exercise title="Three values by hand">

Work these out before writing any code. What should `wrap` give for $3.5\pi$, for $-3.0$ rad, and for
exactly $\pi$?

<Solution>

$3.5\pi$ wraps to $-0.5\pi$, and $-3.0$ rad is already inside the range so it comes back unchanged.
The last one is the interesting case: the interval is half-open, so exactly $\pi$ comes back as
$-\pi$. Decide whether your heading controller cares — for a `kP * error` term it does not, since both
produce the same magnitude of turn in opposite directions and the robot is equidistant either way. For
anything that logs or compares headings for equality, it does.

The doubled `mod` is not decoration: Java and C return a remainder with the sign of the dividend, while
Python does not. That single difference is the most common bug in this function.

</Solution>

</Exercise>

## The completion outcome: `MoveStatus`

This is **Step 5** of the [pipeline](./index.mdx) — and the one piece worth having exactly one copy of.
A follower must distinguish reaching the target from timing out. Both outcomes stop the drivetrain, but
only `REACHED` should advance autonomous policy normally.

<JavaCode label="One completion outcome, used by every follower">{`// Tolerances: tuned once, here, and nowhere else.
static final double POS_TOL = 1.0;                        // inches
static final double HEADING_TOL = Math.toRadians(2);
static final double VEL_TOL = 2.0;                        // inches/second
static final double TIMEOUT = 3.0;                        // seconds, one move

enum MoveStatus { RUNNING, REACHED, TIMED_OUT }

static MoveStatus moveStatus(PoseSample sample, Pose2d target,
                             double timeInMove) {
    double dist = sample.pose().vec().minus(target.vec()).norm();
    double headingErr = Math.abs(
            wrap(target.heading() - sample.pose().heading()));

    boolean settled = dist < POS_TOL
            && headingErr < HEADING_TOL
            && sample.fieldVelocity().norm() < VEL_TOL;

    if (timeInMove > TIMEOUT) return TIMED_OUT;
    if (settled) return REACHED;
    return RUNNING;
}
`}</JavaCode>

<Exercise title="Order of the two checks">

The deadline is checked before `settled`. Construct a case where a late sample lands inside tolerance
after the timeout expired. Which answer do you want, and what goes wrong if the routine treats that run
as a success?

<Solution>

A robot pushed off its path recovers slowly and drifts into tolerance at 3.1 s on a 3.0 s deadline. You
want `TIMED_OUT`, because the deadline exists to bound how long autonomous will spend on one move — and
a `REACHED` here means the routine advances as though everything went to plan, on a schedule it has
already blown. The rest of the routine then runs late with no signal that anything went wrong. Checking
the deadline first makes the deadline mean what it says.

</Solution>

</Exercise>

<Exercise title="Why velocity is in the settled test">

Delete `sample.fieldVelocity().norm() < VEL_TOL` and describe what a robot crossing the target at full
speed now reports.

<Solution>

`REACHED`, for the one loop it happens to be within an inch of the target — while travelling at 40
inches per second and about to be a foot past it. The next move starts from a pose the routine believes
is settled and the robot is nowhere near. The velocity term is what makes "reached" mean *arrived and
stopped* rather than *passed through*.

</Solution>

</Exercise>

`TIMEOUT` is a hard safety deadline, so it takes precedence after it expires even if that same late sample
happens to lie inside the pose tolerances. Choose the deadline with the expected move duration and settling
margin; do not use a late spatial coincidence to mask a failed path.

<Callout type="idea" title="Why one copy matters.">
Each follower used to inline its own version of this test, and they drifted apart — some checked velocity
and heading, one checked only distance. With one <code>moveStatus</code>, every follower stops on both
terminal outcomes while the autonomous routine can separately advance, retry, park, or abort.
</Callout>

## kStatic: the static-friction nudge

Near the goal the proportional command shrinks below what it takes to overcome static friction, stranding
the robot just short. A constant push *in the direction of the error*, applied **only inside a small
band**, defeats it — see [PID-to-point](./pid-to-point.mdx) and [feedforward](../control-theory/feedforward.mdx).

<JavaCode league="FTC" label="kStatic(error)">{`static final double K_STATIC = 0.06;         // power units
static final double K_STATIC_RANGE = 4.0;    // inches, outer edge of the band

// error is robot-frame and signed. Returns a constant push in the direction
// of the error, or zero.
static double kStatic(double error) {
    double e = Math.abs(error);
    if (e > K_STATIC_RANGE) return 0;   // far out: kP is strong enough alone
    if (e < POS_TOL) return 0;          // settled: stop pushing
    return K_STATIC * Math.signum(error);
}
`}</JavaCode>

<Exercise title="Both edges of the band">

The band has two edges and both earn their place. Work out what the robot does if you remove the inner
one, remembering that `sign(error)` flips every time the robot crosses the target.

<Solution>

The push never switches off, so once the robot is at the target the term alternates between $+0.06$ and
$-0.06$ every time noise flips the sign of the error — at loop rate. The robot jitters back and forth
across the target and never reports settled, because `fieldVelocity` never drops below `VEL_TOL`. It
buzzes audibly and the move times out on a target it reached two seconds ago.

</Solution>

</Exercise>

## The drivetrain entry point: `drive(vx, vy, omega)`

Every follower ends by handing a **chassis command** $(v_x, v_y, \omega)$ to the mecanum mixer, which
converts it to four wheel powers and desaturates. That mixer — including field-centric rotation, joystick
shaping, and the desaturation step — is derived in full in
[Mecanum kinematics](./mecanum-kinematics.mdx); the followers just call its entry point:

<JavaCode league="FTC" label="The one call every follower ends with">{`// A robot-frame chassis command in NORMALIZED POWER, each component in [-1, 1]:
// vx forward, vy left, omega CCW. Writes four wheel powers to the motors.
void drive(double vx, double vy, double omega) {
    double[] powers = mixWheelPowers(vx, vy, omega);

    double largest = 1;
    for (double p : powers) largest = Math.max(largest, Math.abs(p));

    for (int i = 0; i < powers.length; i++) powers[i] /= largest;
    setWheelPowers(powers);
}
`}</JavaCode>

:::warning[Convert to normalized power *before* you call this]
The desaturator compares each wheel value against the literal `1`, which only means anything if the
inputs are already fractions of full power. Divide physical speeds by `MAX_SPEED` and `MAX_TURN` at the
call site. Pass raw inches per second instead and every command above about 1 in/s mixes to four equal
values that all divide down to exactly `1.0` — so 5 in/s, 20 in/s, and 40 in/s all come out as full
power, and the entire speed plan is silently discarded.
:::

<Exercise title="What desaturation protects">

Desaturation is the step teams leave out. Work out what happens to a command of $(1.0, 1.0, 0.5)$
without it.

<Solution>

The mix produces wheel powers outside $[-1, 1]$, and `setPower` clips each one independently. Clipping
changes the ratios between the four wheels, and the ratios are what encode direction and turn rate — so
the robot's actual *direction* changes, not just its speed. It curves away from the commanded heading
exactly when the command is largest, which is when the follower is trying hardest to correct.

</Solution>

</Exercise>

<Admonition type="note" title="How the lessons use this page">

When a lesson writes `robot.vec()`, `wrap(...)`, `moveStatus(...)`, `kStatic(...)`, or `drive(...)`, the
definition is here. The lessons show only the part that is genuinely new to that technique — the control
law, the geometry, the speed plan — and link back to this page for the shared plumbing. In your own
codebase these belong in a small `util` package (or you adopt a library's equivalents), written once and
imported by every OpMode rather than copy-pasted.

Implement this page first. Every follower in the module assumes these exist and behave as described, and
a subtle bug in `wrap` or `moveStatus` will look like a bug in the follower that calls it.

</Admonition>
