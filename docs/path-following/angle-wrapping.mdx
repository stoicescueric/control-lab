# Angle Wrapping

<Difficulty level="Easy" />

<Abstract>
Headings go around a circle, so the same direction has many numeric labels, and two angles can be far
apart as numbers while pointing almost the same way. Wrapping every angle difference into
$[-\pi, \pi)$ stops a heading controller from turning the long way around.
</Abstract>

This is a short lesson that fixes a confusing bug. Anything that turns the robot to a heading needs it:
`turnTo`, a heading-hold PID, and the rotation part of [PID-to-point](./pid-to-point.mdx).

<Problem>

## The robot spins 358° to turn 2°

Your robot faces $179°$ and you ask it to turn to $-179°$. That's a $2°$ nudge across "straight back."
The controller computes the error the obvious way:

$$
e = \theta_\text{target} - \theta_\text{current} = -179° - 179° = -358°
$$

and commands a huge $-358°$ turn. The robot spins almost all the way around the wrong way to reach a
heading $2°$ away. A subtler version of the same bug: near that seam the error flips sign from loop to
loop, and the robot wobbles instead of settling.

</Problem>

<Theory>

## Angles are on a circle, not a number line

Adding or subtracting $360°$ doesn't change a direction. So $-179°$ and $+181°$ are the same heading,
and $181° - 179° = +2°$. The subtraction was fine. The answer just needs to be read as a turn around a
circle, picking the shorter way.

<AngleWrapIllustration />

<AngleWrap />

The fix is to **wrap** every angle difference into the range $[-\pi, \pi)$, which is $-180°$ up to (but
not including) $+180°$:

$$
\operatorname{wrap}(e) = ((e+\pi) \bmod 2\pi + 2\pi) \bmod 2\pi - \pi
$$

Try it in degrees on the $-358°$ error. Add $180°$ to get $-178°$. Reduce into one full turn, $0°$ to
$360°$, by adding $360°$: that's $182°$. Subtract $180°$: $+2°$. The shift by $180°$ at the start and end
is what makes the result land between $-180°$ and $+180°$ instead of between $0°$ and $360°$.

An error of exactly $180°$ is a tie, since both ways around are the same distance. This version always
picks $-180°$, so the controller behaves the same way every time.

<Callout type="warn" title="Wrap the error, not just the target">
Wrap the *difference*, every loop, right before it goes into the controller. Wrapping only the target
or only the measurement still leaves a difference that can land outside [-π, π).
</Callout>

</Theory>

<Deploy>

## One helper, used everywhere a heading appears

<JavaCode league="FTC" label="Angle wrapping and a heading hold">{`// The angle in [-pi, pi) pointing the same way as a.
static double wrap(double a) {
    double turn = 2 * Math.PI;
    return ((a + Math.PI) % turn + turn) % turn - Math.PI;
}

double headingPower(double target, double heading) {
    double error = wrap(target - heading);   // this is the entire lesson
    return clamp(kP * error, -1, +1);
}
`}</JavaCode>

<Exercise title="Read the wrap right to left">

Each step has a job:

- `(a + pi)` shifts so the range starts at 0 instead of $-\pi$
- `% turn` reduces to one revolution, but in Java the result can be negative
- `+ turn` then `% turn` forces it positive
- `- pi` shifts back

Why is the second `% turn` there? Try $-3.0$ rad by hand in Java.

<Solution>

In Java, C, and JavaScript, `%` keeps the sign of the number being divided, so `-1.0 % 6.283` is `-1.0`,
not `5.283`. With only one `%`, results can land anywhere in $(-2\pi, 2\pi)$, and after subtracting
$\pi$ some fall outside the range you wanted. Python's `%` is always non-negative, so the second step
does nothing there. That's why code copied from Python without it breaks on the robot.

</Solution>

</Exercise>

<Exercise title="The 340-degree spin">

The target is 170° and the heading is $-170°$. What's `target - heading`, and what does `wrap` turn it
into? Which way does the robot turn, and how far? Now answer again without `wrap`.

<Solution>

`target - heading` is $340°$. Wrapped, that's $-20°$, so the robot turns 20° clockwise, the short way.
Without the wrap, `kP * 340°` maxes out the command and the robot spins 340° counter-clockwise to end up
in the same place, wasting a second or more of the match.

</Solution>

</Exercise>

Use the same `wrap` anywhere two headings are compared: the rotation part of a go-to-pose controller, a
`turnTo`, or the heading feedback in a path follower. Make it a static helper and use it every time you
subtract two angles.

</Deploy>

<Admonition type="note" title="Wrapping vs. unwrapping">

Wrapping keeps an angle in $[-\pi, \pi)$, which is what you want for a control error. The opposite,
*unwrapping*, removes the jumps to make a continuous signal. You want that before computing a turn rate
from heading, or the $2\pi$ jump at the seam looks like an enormous spin.

</Admonition>

<Admonition type="warning" title="Know your IMU's range">

Some IMUs report heading from $-180°$ to $180°$, some from $0°$ to $360°$, and some keep counting past a
full turn. Check the docs, convert to radians once where you read it, and wrap at every comparison
rather than assuming the sensor did it.

</Admonition>
